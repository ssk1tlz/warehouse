# Выпуск релиза

Эта инструкция описывает весь путь от решения «пора выпустить новую версию»
до опубликованного GitHub Release, который увидят пользователи. Выполняется
вручную, на машине разработчика (Windows), с установленными Python, Node.js,
JDK (для Android) и `gh` (GitHub CLI, уже авторизованный — `gh auth login`).

## 1. Что такое релиз

Один тег `vX.Y.Z` в GitHub = ровно два артефакта, собранные из одного и того
же коммита:

- `installer/output/WarehouseSetup-X.Y.Z.exe` — установщик Windows (desktop);
- `mobile/android/app/build/outputs/apk/release/app-release.apk` — подписанный
  APK для Android.

Номер версии для обоих артефактов берётся из одного источника — файла
`VERSION` в корне репозитория (сейчас там `1.0.0`). Всё остальное
генерируется из него скриптом `bump_version.py` и коммитится в репозиторий:

- `VERSION` — сама версия, например `1.0.1`;
- `mobile/www/js/version.js` — `window.APP_VERSION = '1.0.1';`, версия для
  мобильного веб-кода;
- `mobile/android/version.properties` — `versionName`/`versionCode` для
  Android-сборки (формула `versionCode` — см. раздел 7).

Desktop (`server.py`) читает версию из файла `VERSION` при старте сервера.
Мобильное приложение читает `window.APP_VERSION`, зашитый в JS-бандл на
этапе сборки APK. Поэтому файлы версии должны быть сгенерированы (и,
для мобильного приложения, синхронизированы в Android-проект — раздел 4)
**до** сборки установщика и APK — иначе один из артефактов унесёт в релиз
старый номер версии.

Проверить в любой момент, что все файлы версии в синхроне с `VERSION`:

```bash
python bump_version.py --check
```

Если файлы разошлись (например, кто-то отредактировал `VERSION` вручную),
пересобрать их без изменения самой версии:

```bash
python bump_version.py --sync
```

## 2. Разовая подготовка: ключ подписи Android

Ключ подписи создаётся один раз — не на каждый релиз — и используется для
**всех** последующих релизов Android-приложения. Причина: Android допускает
установку обновления поверх уже установленного приложения только если новый
APK подписан тем же сертификатом, что и старый. Другими словами:

> **Потеря ключа (файла `.jks` или пароля к нему) означает, что обновления
> приложения больше не установятся поверх старых.** Единственный обходной
> путь в этом случае — выпустить приложение заново под другим `applicationId`
> и попросить всех пользователей вручную удалить старую версию перед
> установкой новой. Храните резервную копию `.jks`-файла и пароль в надёжном
> месте вне репозитория (менеджер паролей, зашифрованный архив на другом
> носителе) — не только там, где лежит рабочая копия ключа.

Создать папку вне репозитория и сам ключ:

```bash
mkdir -p "$USERPROFILE/.warehouse-release"
keytool -genkeypair -v \
  -keystore "$USERPROFILE/.warehouse-release/warehouse.jks" \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias warehouse \
  -dname "CN=Warehouse, OU=IT, O=Warehouse, L=-, S=-, C=RU" \
  -storepass <ПАРОЛЬ> -keypass <ПАРОЛЬ>
```

`keytool` входит в состав JDK. Если его нет в `PATH`, вызывайте по полному
пути (пример с этой машины: `"C:\Program Files\Eclipse
Adoptium\jdk-21.0.12.101-hotspot\bin\keytool.exe"` — у вас путь будет
зависеть от установленного JDK).

Пароль — не запоминать вручную, а сгенерировать случайный и сразу сохранить
в `keystore.properties` (следующий шаг), не показывая его в терминале лишний
раз:

```bash
python -c "import secrets; print(secrets.token_urlsafe(24))"
```

Затем скопировать образец в реальный (не коммитящийся) файл:

```bash
cp mobile/android/keystore.properties.example mobile/android/keystore.properties
```

и заполнить `mobile/android/keystore.properties` реальными значениями
(формат — как в `keystore.properties.example`; обратите внимание на
двойные обратные слэши в пути — так требует формат `.properties`):

```properties
storeFile=C:\\Users\\<ваш пользователь>\\.warehouse-release\\warehouse.jks
storePassword=<пароль>
keyAlias=warehouse
keyPassword=<пароль>
```

Файл `mobile/android/keystore.properties`, как и сам `.jks`, в репозиторий
никогда не коммитится (`.gitignore`: `mobile/android/keystore.properties`,
`*.jks`, `*.keystore`) — только `keystore.properties.example` с плейсхолдерами.
Если `keystore.properties` отсутствует или заполнен не полностью, релизная
сборка (`./gradlew.bat assembleRelease`) падает с понятной ошибкой на русском,
а не тихо создаёт debug-подписанный APK.

## 3. Разовая подготовка: Inno Setup

Установщик Windows собирается компилятором Inno Setup 6:

```bash
winget install -e --id JRSoftware.InnoSetup
```

Дополнительная настройка не нужна: `installer/build_installer.bat`
автоматически ищет `ISCC.exe` — сначала в переменной окружения `ISCC` (если
задана), затем в `%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe`
(пользовательская установка), затем в `%ProgramFiles(x86)%\Inno Setup
6\ISCC.exe` (установка для всех пользователей). Если winget поставил
компилятор в одно из этих мест — а он это делает по умолчанию — ничего
больше настраивать не требуется.

## 4. Выпуск новой версии

Все команды выполняются из корня репозитория.

**Шаг 1. Поднять версию.** `bump_version.py` печатает новый номер версии в
stdout и перезаписывает `VERSION`, `mobile/www/js/version.js`,
`mobile/android/version.properties`:

```bash
python bump_version.py patch     # 1.0.0 -> 1.0.1 (или minor / major)
```

**Шаг 2. Прогнать тесты.**

```bash
python -m pytest -q
node --test mobile/tests/*.test.js
```

**Шаг 3. Закоммитить файлы версии.** Тег в шаге 6 должен указывать на коммит,
в котором версия во всех трёх файлах уже совпадает с номером тега:

```bash
git add VERSION mobile/www/js/version.js mobile/android/version.properties
git commit -m "release: v1.0.1"     # подставить реальный номер версии
```

**Шаг 4. Собрать установщик Windows.** `installer/build_installer.bat`
сам проверяет синхронность версии (`bump_version.py --check`), пересобирает
`dist/WarehouseApp_New.exe` через PyInstaller и упаковывает его в установщик:

```bash
installer/build_installer.bat
```

Результат: `installer/output/WarehouseSetup-1.0.1.exe` (имя файла собирается
из `WAREHOUSE_VERSION`, которую скрипт читает из `VERSION` — см.
`installer/warehouse.iss`, `OutputBaseFilename=WarehouseSetup-{#MyAppVersion}`).

**Шаг 5. Собрать подписанный APK.**

```bash
cd mobile && npx cap sync android && cd android && ./gradlew.bat assembleRelease
```

`npx cap sync android` здесь **обязателен**, а не опционален. Capacitor не
пересобирает Android-проект на лету: `mobile/android/app/src/main/assets/public`
— это отдельная скопированная копия каталога `mobile/www` (см.
`mobile/capacitor.config.json`, `webDir: "www"`), и Gradle при сборке APK
берёт JS именно из этой копии, а не из `mobile/www` напрямую. Если пропустить
`cap sync`, Gradle упакует в APK ту версию JS (включая старый
`window.APP_VERSION` из шага 1), которая была скопирована туда при
**предыдущей** сборке — то есть APK молча уедет в релиз со старым кодом и
старым номером версии внутри. Именно это уже случилось в конце Этапа 1
проекта — с тех пор `cap sync` в этом документе идёт явным обязательным
шагом, а не предположением.

Результат: `mobile/android/app/build/outputs/apk/release/app-release.apk`,
подписанный ключом из раздела 2 (если `keystore.properties` отсутствует или
неполон, сборка упадёт на этапе конфигурации с русской ошибкой — см. раздел 2).

**Шаг 6. Тег и публикация релиза.**

```bash
git tag v1.0.1 && git push origin master --tags

gh release create v1.0.1 \
  installer/output/WarehouseSetup-1.0.1.exe \
  mobile/android/app/build/outputs/apk/release/app-release.apk \
  --title "v1.0.1" --notes "..."
```

(`--notes "..."` — заменить на реальное описание релиза; либо передать
`--notes-file <файл>`, либо `--generate-notes`, чтобы `gh` собрал список
изменений из коммитов автоматически.)

## 5. Что видит пользователь

Desktop-приложение проверяет обновления в фоне: при старте сервера и затем
не чаще раза в сутки (интервал отсчитывается от последней **успешной**
проверки — временное отсутствие сети не мешает попытке на следующий день).
Проверка — анонимный GET-запрос к публичному GitHub API
(`https://api.github.com/repos/ssk1tlz/warehouse/releases/latest`), без
какой-либо телеметрии.

Если найдена версия новее текущей, в интерфейсе появляется плашка:

> Доступна версия X (у вас Y).

со ссылкой на страницу релиза на GitHub. Скачивание и установка — целиком
вручную: приложение ничего не скачивает и не устанавливает само, только
сообщает о наличии новой версии.

Условия показа:

- проверка обновлений включена в настройках (чекбокс «Проверять обновления
  (раз в сутки, через интернет)» в диалоге настроек; включена по умолчанию);
- прошли сутки с последней успешной проверки на этой машине (при первом
  запуске после обновления до этой версии приложения кэш пуст, поэтому первая
  проверка происходит сразу же);
- приложение запущено (или открыт его веб-интерфейс) хотя бы один раз в
  течение суток после публикации релиза — сама по себе публикация релиза на
  GitHub ничего никому не «проталкивает».

## 6. Предупреждение SmartScreen

При первом запуске `WarehouseSetup-X.Y.Z.exe` Windows может показать синее
окно «Windows защитила ваш компьютер». Это не вирус и не ложное
срабатывание антивируса — так SmartScreen реагирует на любую программу без
платного сертификата подписи кода (такой сертификат стоит отдельных денег и
никак не влияет на работу самой программы). Чтобы продолжить установку:
нажать «Подробнее», затем «Выполнить в любом случае».

Формулировка намеренно совпадает с той, что уже видит пользователь в
`README.txt`, `ИНСТРУКЦИЯ.txt` и `БЫСТРЫЙ_СТАРТ.txt` — эта инструкция ничего
нового не обещает, только объясняет то же самое разработчику. Если в
будущем будет куплен сертификат подписи кода (платный, продлевается
ежегодно), это предупреждение перестанет появляться — но сама по себе смена
подписи установщика не связана с ключом подписи Android из раздела 2, это
два независимых механизма.

## 7. Ограничения

**`versionCode` требует `minor` и `patch` меньше 100.** Android-versionCode
считается как `major * 10000 + minor * 100 + patch` (см.
`bump_version.py:version_code`). Если `minor` или `patch` достигнет 100,
`bump_version.py` откажется генерировать файлы версии с понятной ошибкой —
это защита от коллизии: например, `1.0.100` и `1.1.0` дали бы один и тот же
`versionCode` (10100), из-за чего Android отказался бы ставить «обновление»
без вменяемой причины. При текущем темпе релизов (сотни minor/patch-версий)
это далёкий предел, но при выпуске 100-й patch-версии в рамках одного minor
придётся сначала поднять minor.

**Тег релиза должен быть строго в формате `vX.Y.Z`** — ровно три числа через
точки, без каких-либо суффиксов вроде `-beta`, `-rc1` или `-nightly` (буква
`v` в начале — конвенция этого документа; сама проверка обновлений разбирает
тег регулярным выражением `^[vV]?(\d+)\.(\d+)\.(\d+)$` из `updates.py`, так
что технически подошёл бы и тег без `v`, но каждый пример в этом документе
использует `v`, чтобы конвенция была одна). Любой тег, не подходящий под
этот шаблон, проверка обновлений просто молча проигнорирует — GitHub-релиз
с таким тегом останется доступным по прямой ссылке, но плашка «Доступна
версия» пользователям показана не будет. Это осознанная защита от того,
чтобы «nightly»/тестовый релиз случайно предложили всем пользователям как
обновление, а не ошибка и не повод паниковать, если такой тег понадобился.
(Дополнительно: если пометить релиз на GitHub как предварительный (флаг
`--prerelease` у `gh release create`), `/releases/latest` его тоже не
вернёт — второй, независимый способ выпустить тестовую сборку так, чтобы
обычные пользователи её не увидели.)
