Warehouse: путь к массовому запуску

Что добавить и что исправить, чтобы связка «десктоп-сервер + Android-сканер» превратилась из внутреннего инструмента в продукт, который можно ставить чужим людям на чужие склады. Оценки основаны на текущем коде проекта.

00

Что уже сильно

Это фундамент, который не нужно переделывать — на нём стоит всё остальное.

  • Офлайн-first мобильное приложение: локальный кэш, очередь действий, защита от дублей (mobile_action_log)
  • QR-сопряжение телефона с сервером — подключение без ручного ввода адреса
  • Журнал аудита всех изменений уже в схеме БД
  • Полностью офлайн: ни одной CDN-зависимости
  • Автоснапшоты базы при изменениях в backups/
  • Генерация актов приёма-передачи с нумерацией
  • Сборка в один EXE + трей-приложение + автозапуск
  • Тесты на критичную серверную логику и разбор QR
01

Исправить до запуска

Дыры, которые простительны внутреннему инструменту и непростительны продукту.

Безопасность передачи и входа

обязательноL

Перевести LAN-обмен на HTTPS (самоподписанный сертификат, отпечаток зашивается в QR сопряжения — телефон доверяет только своему серверу). Вместо одного общего пароля — учётные записи с ролями: администратор, кладовщик, просмотр. Токены вместо Basic-auth.

сейчас — пароль один на всех и летит по сети открытым HTTP в base64; любой в той же Wi-Fi-сети может его перехватить и писать в базу.

Версионные миграции схемы БД

обязательноM

Таблица schema_version и упорядоченный список миграций. У чужих пользователей будут все версии базы вперемешку — обновления должны применяться предсказуемо и с автобэкапом перед миграцией.

сейчас — набор ad-hoc проверок «если колонки нет — ALTER TABLE» в init_db(); работает, но не масштабируется на годы обновлений.

Установщик, подпись, обновления

обязательноM

Windows: установщик (Inno Setup / MSI) вместо набора bat-файлов, подпись кода — иначе SmartScreen пугает каждого нового пользователя. Android: подписанный release-APK вместо debug-сборки, публикация в RuStore / Google Play. Обоим — механизм автообновления или хотя бы проверку «доступна новая версия».

сейчас — неподписанный EXE + bat-скрипты и debug-APK, который ставится только через «разрешить неизвестные источники».

Конфликты и целостность при синхронизации

обязательноM

Определить правила: что происходит, когда технику правят одновременно с десктопа и с телефона, у которого действие лежало в очереди офлайн. Минимум — версия записи и понятное сообщение «данные изменились, обновите»; включить SQLite WAL для параллельных читателей.

сейчас — последняя запись побеждает молча; при одном кладовщике незаметно, при трёх — потерянные правки.

Человеческие ошибки вместо alert()

важноS

Тосты и встроенные состояния в мобильном приложении: подтверждение «действие в очереди», ошибка сервера в очереди — по ТЗ на дизайн. Плюс восстановление из бэкапа в один клик на десктопе (снапшоты уже делаются — интерфейса восстановления нет).

02

Добавить: функции, которые продают продукт

В порядке отдачи на вложенный час. Первые две — то, ради чего складские команды выбирают инструмент.

Режим инвентаризации

важноL

Киллер-фича сканера: запускаешь «Инвентаризацию», ходишь по складу и сканируешь всё подряд — приложение отмечает найденное, а в конце отдаёт расхождения: чего не хватает, что лишнее, что не на своём месте. Отчёт уходит на десктоп и в акт.

сейчас — сканер умеет только открывать карточку по одной единице; сверка склада руками.

Печать QR-этикеток пачкой

важноM

Мастер на десктопе: выбрать позиции → лист этикеток под обычный принтер или ленточный термопринтер (название, инв. №, QR). Без удобной печати этикеток сканер не взлетает у новых пользователей — им нечего сканировать.

Распознавание этикеток: серийник и модель с фото

в работеM

Заполнение карточки техники «наведи камеру»: заводской штрихкод на этикетке даёт точный серийный номер, а распознавание текста (Google ML Kit, работает на устройстве — офлайн и бесплатно, без облачных API) вытаскивает производителя, модель и категорию. Поля формы предзаполняются, последнее слово — за человеком. Собственную нейросеть обучать не нужно.

статус — первые два этапа реализованы в августе 2026: на экране редактирования мобильного приложения появились кнопки «Штрихкод → серийный №» и «Распознать этикетку»; разбор этикетки покрыт юнит-тестами. Возможное развитие: автозаполнение гарантии по публичным API производителей (Dell/Lenovo/HP) через десктопный сервер.

Уведомления по гарантии и минимальным остаткам

важноS

Поля warranty_end и min_quantity уже есть в базе — осталось показать: панель «требует внимания» на десктопе (гарантия истекает за 30 дней, остаток ниже минимума) и счётчик на мобильном.

Экран «сотрудник» на мобильном

важноS

«Что на руках у Иванова» — список закреплённой техники с быстрым возвратом. Особенно вместе со свежим полем «статус сотрудника»: при увольнении — чек-лист сдачи техники одним экраном.

Фото техники

ростM

Поле photo_url уже в схеме. Камера телефона — естественный источник: сфотографировал при приёмке — фото в карточке и в акте (состояние техники при выдаче/возврате).

Отчёты и экспорт

ростM

Экспорт в Excel/CSV (ведомость по отделу, по сотруднику, движения за период), итоги по стоимости. Графики на десктопе уже есть — не хватает выгрузки, которую можно отдать бухгалтерии.

Живая синхронизация вместо опроса раз в 15 секунд

ростM

Server-Sent Events или WebSocket: изменения на десктопе прилетают на телефоны мгновенно, телефон меньше жжёт батарею впустую. Текущий опрос — нормальный компромисс для старта, менять не срочно.

04

Порядок работ

Здравый маршрут: сначала раздел 01 целиком (безопасность → миграции → упаковка → конфликты) — это «лицензия на запуск». Параллельно с упаковкой — новый дизайн мобильного приложения по готовому ТЗ. Затем две продающие фичи: печать этикеток и инвентаризация. После этого продукт можно показывать первым чужим пользователям, а разделы «рост» и «масштаб» наполнять по их отзывам, а не по догадкам.
