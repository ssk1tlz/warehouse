# Справочник обозначений техники и создание карточек с телефона — дизайн

## Контекст

Инвентарные номера в базе сейчас в двух несовместимых форматах. Из 203
единиц:

- **175** — голая нумерация `001`…`181` (три цифры, без префикса, с
  дырами 048, 061-064, 066);
- **28** — сквозная нумерация с буквенным префиксом по типу техники,
  проставленная вручную: `SVR-0001`…`SVR-0003`, `UPS-0004`,
  `RTR-0005`…`RTR-0012`, `SW-0013`, `AP-0014`, `AP-0015`, `SW-0016`,
  `SW-0017`, `TAB-0018`…`TAB-0020`, `NB-0021`, `MFP-0023`, `PC-0024`,
  `MON-0025`, `MFP-0026`, `KEY-0027`, `MUS-0028`, `SCN-0029` (номер 0022
  пропущен).

Числовые части двух форматов пересекаются: голый `001` и `SVR-0001` — это
одно и то же число у разных единиц. Цель этапа — привести всё к одному
виду `ПРЕФИКС-NNNN` со сквозной нумерацией и сделать так, чтобы префикс и
номер присваивались сами, а не вписывались руками.

Категория — свободный текст, 44 различных значения на 203 единицы, с
разнобоем: «Принтер / Сканер» и «Принтер  Сканер» (два пробела),
«Коммутатор», «Kоммутатор» (латинская `K`), «Коммутатор-свитч»,
«PoE-коммутатор (свитч)». Поэтому тип определяется поиском ключевых слов
по строке «категория + наименование», а не точным совпадением категории.

### Уже есть и переиспользуется

- **`getNextInventoryNumber()` / `autoFillInventoryNumber()`**
  (`app.js:651-714`) — кнопка 📋 у поля инв. номера, берёт последний
  номер вида `БУКВЫ-ЦИФРЫ` и увеличивает его, префикс копирует из
  найденного. Тип техники не учитывает. Это точка, которую заменяет
  Задача C.
- **`guessCategory(text, model)`** (`mobile/www/js/label.js:86`) —
  распознавание типа по ключевым словам для заводских этикеток, уже
  возвращает русские категории («Ноутбук», «Монитор», «Принтер», «МФУ»,
  «Сервер»). Прецедент подхода; правила Задачи A устроены так же, но
  живут на сервере и покрывают все типы.
- **`applyLabelToEditForm(parsed)`** (`mobile/www/js/screens.js:335`) —
  подстановка распознанного с этикетки в пустые поля формы, непустые не
  трогает. Форма создания переиспользует ровно эту функцию.
- **`apply_action()` + `mobile_action_log`** (`mobile_actions.py:442`) —
  идемпотентная очередь по `clientActionId`: повторная отправка
  возвращает закэшированный ответ вместо второго применения. Создание
  становится ещё одним типом в `_DISPATCH` и получает идемпотентность
  бесплатно.
- **Бамп `state_version` на каждое мобильное действие**
  (`server.py:1247`) и проверка `base_version` при сохранении с десктопа
  (`server.py:1018`, ответ 409 + свежее состояние). Благодаря этому
  техника, заведённая с телефона, не может быть затёрта устаревшим
  `import_state()` с компьютера — тот сначала получит 409 и перезагрузит
  состояние. Отдельная защита не нужна.
- **Роли на `/api/mobile/action`** — `admin` и `storekeeper`
  (`server.py:982`), те же, что на сохранении состояния. Создание
  наследует их без изменений.
- **Очередь отложенной загрузки фото** (`Sync.retryPendingPhotoUploads`,
  `mobile/www/js/sync.js:171`, таблица `pending_photo_uploads`) —
  ключуется по `assetId`, а id генерирует клиент. Значит фото новой
  техники снимается офлайн и уезжает вместе с карточкой.
- **Таблица `meta` в мобильной SQLite** (`mobile/www/js/db.js`, приём
  `activeInventorySession`) — место для кэша справочника на телефоне.
- **Система версионированных миграций** (`migrations.py`, `MIGRATIONS`,
  сейчас 027) — миграция применяется сама при старте сервера, в том
  числе в собранном `.exe`. Пользователю не нужно запускать Python.
- **`auto_backup()`** (`server.py`) — резервная копия базы перед
  изменяющими операциями.

## Не-цели

- **Редактируемый справочник в интерфейсе.** Решение зафиксировано с
  пользователем: справочник вшит в код, в приложении только просмотр.
  Новое обозначение добавляется правкой одного списка в `asset_codes.py`.
- **Смена префикса при смене категории у существующей карточки.**
  Инвентарный номер — идентификатор, напечатанный на этикетке. Если
  монитор `MON-0008` переклассифицировали, номер остаётся `MON-0008`.
  Автоподстановка работает только при заведении новой карточки.
- **Переиспользование освободившихся номеров.** Списанная техника номер
  не возвращает; счётчик только растёт.
- **Изменение складского учёта.** Выдача, возврат, ремонт, списание не
  трогаются.
- **Создание сотрудников, отделов, площадок с телефона.** Только
  техника.
- **Количество больше 1 с телефона.** Форма создаёт одну единицу
  (`quantity = 1`); партии заводятся с компьютера.

## Задача A: справочник обозначений, сервер как источник номеров

### Почему на сервере

Телефон в офлайне не знает настоящего максимума по базе: два телефона без
сети оба выберут `0204`. Единственное место, где номер можно выдать без
гонки, — сервер, под уже существующим `STATE_LOCK`. Решение зафиксировано
с пользователем.

**Десктоп — исключение, и это не противоречие.** Сохранение состояния с
компьютера защищено проверкой `base_version` (`server.py:1018`): если
телефон завёл технику после того, как десктоп в последний раз получил
состояние, десктоп получит 409 и перезагрузит данные, а не сохранит
поверх. Значит в момент успешного сохранения максимум, посчитанный в
`app.js`, гарантированно актуален, и номер, показанный в форме, —
окончательный. `import_state()` не трогается: он по-прежнему берёт номер
из присланного состояния.

Серверное присвоение нужно ровно там, где этой защиты нет — в мобильных
действиях, которые приходят из офлайн-очереди с произвольной задержкой.

### Новый модуль `asset_codes.py`

Отдельный файл, без импортов `http.server` — по образцу
`mobile_actions.py`, чтобы тестировался независимо.

```python
ASSET_CODE_RULES: list[tuple[str, str, tuple[str, ...]]]
# (префикс, человекочитаемое название, ключевые слова)
```

Порядок правил значим и является частью контракта: «моноблок»
проверяется раньше «пк», «принтер / сканер» раньше «принтер», иначе
более общее правило перехватит частное. Тест фиксирует порядок.

Справочник — 28 обозначений (в скобках — сколько единиц попадает по
текущей базе, сумма 203, нераспознанных нет):

| Префикс | Тип | шт. | Префикс | Тип | шт. |
|---|---|--:|---|---|--:|
| `MUS` | Мышь (проводная/беспроводная) | 31 | `AC` | Кондиционер | 6 |
| `MON` | Монитор | 24 | `SW` | Коммутатор / свитч | 5 |
| `PC` | Системный блок | 23 | `AIO` | ПК-моноблок | 3 |
| `KEY` | Клавиатура (проводная/беспроводная) | 20 | `NVR` | Видеорегистратор | 3 |
| `MFP` | МФУ (принтер + сканер) | 17 | `WC` | Кулер для воды | 3 |
| `RTR` | Роутер | 12 | `TAB` | Планшет | 3 |
| `SPK` | Акустика / колонки | 11 | `SVR` | Сервер | 3 |
| `UPS` | ИБП | 8 | `REF` | Холодильник | 2 |
| `NB` | Ноутбук | 7 | `TV` | Телевизор | 2 |
| `PRN` | Принтер | 7 | `SCN` | Сканер | 2 |
| `CAM` | Веб-камера | 2 | `PLT` | Плоттер | 1 |
| `HPH` | Наушники | 2 | `CFM` | Кофемашина | 1 |
| `AP` | Точка доступа | 2 | `KTL` | Электрочайник | 1 |
| `TEL` | Стационарный телефон | 1 | `AVR` | Стабилизатор напряжения | 1 |

`PRN` и `MFP` разделены (решение зафиксировано с пользователем):
«Принтер / Сканер» и «МФУ» → `MFP`, «Принтер» и «Цветной принтер» →
`PRN`. Уже проставленные вручную `MFP-0023` и `MFP-0026` (категория
«Принтер», но модели EPSON L3560 и M2110 — действительно МФУ) остаются
`MFP`: миграция ручные буквы не пересматривает.

Резервное обозначение — `INV`, когда не сработало ни одно правило. По
текущей базе таких нет, но новая техника может не попасть ни в одно.

### Функции

```python
def guess_prefix(category: str, name: str) -> str
```
Склеивает `category + " " + name`, приводит к нижнему регистру,
нормализует `ё → е`, идёт по `ASSET_CODE_RULES` по порядку и возвращает
префикс первого правила, чьё ключевое слово входит в строку. Иначе
`"INV"`.

```python
def next_number(connection) -> int
```
Максимум числовой части по всем непустым `assets.inventory_number`
(и `ПРЕФИКС-NNNN`, и голых цифр — на случай, если что-то осталось), плюс
1. Пустая база → 1.

```python
def assign_inventory_number(connection, category: str, name: str) -> str
```
`f"{guess_prefix(...)}-{next_number(...):04d}"`. Вызывается только внутри
транзакции под `STATE_LOCK`, поэтому гонки между телефонами нет.

### Публикация справочника клиентам

`export_state()` (`server.py:540`) добавляет в ответ `GET /api/state`:

```json
"assetCodeTypes": [{"prefix": "NB", "label": "Ноутбук",
                    "keywords": ["ноутбук", "laptop", "notebook"]}, ...]
```

Так правила остаются в одном месте (Python), а десктоп и телефон
показывают одинаковый справочник и считают одинаковый предварительный
номер, не имея собственной копии списка. Это дешевле, чем
синхронизировать два списка тестом на совпадение.

`import_state()` присланный `assetCodeTypes` игнорирует — поле
только на чтение, как `currentVersion` и `attentionItems`.

## Задача B: перенумерация 203 единиц (`_migrate_028`)

Разовая миграция в `migrations.py`, применяется сама при старте сервера.
Решение о сквозной перенумерации без дыр зафиксировано с пользователем.

Порядок присвоения — сначала 175 голых в порядке возрастания их текущего
числа, затем 28 префиксных в порядке возрастания их числа:

| Было | Стало |
|---|---|
| `001` Системный блок | `PC-0001` |
| `005` Ноутбук | `NB-0005` |
| `008` Монитор | `MON-0008` |
| … | … |
| `181` Ноутбук Acer lite 15 | `NB-0175` |
| `SVR-0001` | `SVR-0176` |
| … | … |
| `SCN-0029` | `SCN-0203` |

Итог — сплошной диапазон `0001`-`0203`, следующая заведённая единица
получает `0204`.

Правила:

- **Буквы у 28 префиксных сохраняются как есть**, даже когда расходятся с
  правилами справочника: `RTR-0007` («Без категории» / «Opical Network
  Terminal») и `UPS-0004` (категория «Периферийные устройства», название
  «Источник Бесперебойного Питания») проставлены вручную осознанно.
  Меняется только число.
- **У 175 голых префикс вычисляется** через `guess_prefix()`.
- **`rev` увеличивается на 1** у каждой изменённой строки, иначе телефон
  с закэшированной карточкой не увидит новый номер как изменение.
- **`state_version` увеличивается**, чтобы открытый десктоп получил 409 и
  перезагрузил состояние вместо сохранения поверх старыми номерами.
- **Идемпотентность**: миграция защищена `schema_version`, повторно не
  применяется. Дополнительно — если ни одной строки с голым номером нет и
  все номера уникальны, миграция ничего не делает.
- **Резервная копия** базы через `auto_backup()` перед изменениями.

Печать этикеток миграция не ломает: `label_printed_at` пуст у всех 203 —
через приложение этикетки ни разу не печатались.

## Задача C: автоподстановка и справочник в десктопной форме

### Автоподстановка

`getNextInventoryNumber()` и `autoFillInventoryNumber()`
(`app.js:651-714`) заменяются на логику, учитывающую тип:

- при вводе в поля «Категория» и «Наименование» поле «Инв. номер»
  заполняется как `ПРЕФИКС-NNNN`, где префикс берётся по
  `assetCodeTypes` из состояния, а число — максимум по базе + 1;
- пока номер не тронут руками, он пересчитывается при каждой смене
  категории или наименования; как только пользователь отредактировал
  поле, приложение в него больше не пишет. Признак «номер сгенерирован
  автоматически» держится в поле `dataset.autoGenerated` инпута и
  сбрасывается по событию `input` от пользователя;
- кнопка 📋 остаётся и принудительно перезаписывает поле, снова включая
  автоматический режим;
- в режиме редактирования существующей карточки автоподстановка не
  срабатывает — проверка `assetId.value !== ""` уже есть в
  `updateInventoryHint()`.

Номер, показанный на десктопе, — **окончательный**: проверка
`base_version` не даст сохранить поверх устаревшего состояния, поэтому
максимум в момент сохранения актуален (см. Задачу A). Предварительным
номер бывает только на телефоне.

### Модалка «Справочник обозначений»

Кнопка-ссылка рядом с полем инв. номера открывает модальное окно с
таблицей из `assetCodeTypes`: префикс, тип, количество единиц этого типа
в базе. Только просмотр. Разметка и стили — по образцу уже существующих
модалок (`index.html`, `styles.css`).

## Задача D: создание техники в мобильном приложении

> **ОТЛОЖЕНА (решение от 2026-09-06).** Делаются A, B и C; D остаётся
> описанной здесь и берётся отдельно. Задачи A-C от неё не зависят:
> справочник живёт на сервере ради миграции из Задачи B, а не ради
> телефона, так что D потом ложится на готовое без переделок.

### Серверная часть

Новый тип действия `create` в `_DISPATCH` (`mobile_actions.py`):

```python
def apply_create(connection: sqlite3.Connection, action: dict) -> dict
```

- `assetId` генерирует клиент, поэтому проверка «`assetId` обязателен»
  в `apply_action()` (`mobile_actions.py:447`) остаётся в силе без
  изменений, а идемпотентность по `clientActionId` работает как для
  остальных типов: повтор вернёт тот же `assetId` и тот же номер.
- Поля берутся те же, что у `apply_edit` — `name`, `category`,
  `serialNumber`, `location`, `purchaseDate`, `warrantyEnd`. Плюс
  `quantity = 1`, `status = 'in_stock'`, `rev = 0`; остальные колонки —
  по умолчанию из схемы. `apply_edit` намеренно не трогает
  количество и статус, потому что они завязаны на учёт распределений; у
  новой карточки распределений нет, поэтому фиксированная единица
  безопасна.
- `inventory_number` **не берётся из запроса**, а вычисляется
  `asset_codes.assign_inventory_number(connection, category, name)` уже
  внутри транзакции. Присланный клиентом номер игнорируется.
- Отклоняется с `MobileActionError`, если `name` пустое или карточка с
  таким `assetId` уже есть (не replay, а коллизия id).
- Пишет движение типа **`purchase`** в `movements` с текстом «Заведена
  карточка техники (с телефона)». Именно `purchase`, а не новый тип:
  десктоп при добавлении техники пишет ровно его (`app.js:2983`), и
  только он есть в `movementLabels` («Поступление», `app.js:24`). Новый
  тип отрисовался бы в истории сырой строкой и разошёлся бы с десктопом
  для одного и того же события.
- Возвращает `{"assetId": ..., "inventoryNumber": ..., "rev": 0}`, чтобы
  телефон показал реально присвоенный номер.

Разрешения не меняются: `admin` и `storekeeper`, как у всей
`/api/mobile/action`.

### Клиентская часть

Новый экран `screen-create` — по образцу `screen-edit`, те же поля плюс
кнопка съёмки фото. Инвентарный номер на нём **не редактируется**:
показывается предварительное значение с пометкой, что окончательный
номер присвоится при синхронизации. Предварительный номер считается из
кэша `assetCodeTypes` (таблица `meta`, приём `activeInventorySession`) и
максимума по локальной таблице `assets`.

Три входа в форму (все три выбраны пользователем):

1. **Кнопка «Добавить технику» на главном экране** (`screen-scan`, рядом
   с блоком последних действий). Скрыта у роли `viewer` тем же приёмом
   `classList.toggle('hidden', ...)`, что и пункт «Инвентаризация».
2. **После скана неизвестного кода.** Сейчас это тупик с тостом
   «Этот QR не найден в кэше» (`screens.js:201`). Добавляется кнопка
   «Завести карточку», а если распозналась заводская этикетка — поля
   заполняются через существующий `applyLabelToEditForm()`.
3. **Из пустого результата поиска** — вместо «Ничего не найдено»
   (`screens.js:441`) кнопка завести с подставленным названием из строки
   поиска.

Отправка кладёт действие в ту же очередь `Db.enqueueAction()`, что и
редактирование, и работает офлайн. Фото уходит через
`uploadOrQueuePhoto()` по клиентскому `assetId`.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Тип техники не распознан | Префикс `INV`, номер выдаётся как обычно. Ошибки нет. |
| Телефон офлайн | Действие в очереди, предварительный номер на экране, окончательный приходит после синхронизации. |
| Два телефона завели технику офлайн | Оба получают разные номера: сервер выдаёт их последовательно под `STATE_LOCK`. |
| Предварительный номер на телефоне разошёлся с присвоенным | Тост с фактическим номером после синхронизации. На десктопе такого не бывает: там номер окончательный. |
| Десктоп сохраняет поверх устаревшего состояния | Существующая проверка `base_version` → 409 → перезагрузка состояния. Новый код не нужен. |
| Повторная отправка действия `create` | `mobile_action_log` возвращает закэшированный ответ, второй карточки не появляется. |
| Миграция запущена дважды | `schema_version` не даёт применить повторно. |

## Тестирование

По TDD, тесты пишутся до реализации.

**`asset_codes`**
- Каждое из 28 правил возвращает свой префикс на реальном примере из
  базы.
- Порядок правил: «Принтер / Сканер» → `MFP`, а не `PRN`; «ПК -
  моноблок» → `AIO`, а не `PC`.
- «Kоммутатор» с латинской `K` → `SW`.
- Двойной пробел в «Принтер  Сканер» → `MFP`.
- Неизвестный тип → `INV`.
- `next_number` на пустой базе → 1; при смеси голых и префиксных номеров
  берёт настоящий максимум.

**`_migrate_028`**
- На копии реальной базы: 203 номера, все уникальны, диапазон
  `0001`-`0203` без дыр.
- Буквы 28 ручных позиций не изменились, включая `RTR-0007` и `UPS-0004`.
- `rev` вырос у каждой изменённой строки, `state_version` вырос.
- Повторный запуск ничего не меняет.

**`apply_create`**
- Заводит карточку и присваивает номер по типу.
- Повтор с тем же `clientActionId` не создаёт вторую карточку и
  возвращает тот же номер.
- Присланный клиентом `inventoryNumber` игнорируется.
- Пустое `name` отклоняется.
- Два последовательных создания получают разные номера.
- Записывает движение типа `purchase`, а не какой-либо новый тип.

**Десктоп (`app.js`)**
- Автоподстановка срабатывает при вводе категории и не трогает поле
  после ручной правки.
- В режиме редактирования не срабатывает.
