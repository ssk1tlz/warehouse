# Рабочие места (столы) — дизайн

## Контекст

Техника сейчас числится ровно за одним получателем из трёх: сотрудник,
отдел или объект. Запись о выдаче (`asset_allocations`) хранит
`employee_id`, `department` и `site`, из которых заполнено ровно одно —
это проверено на живой базе: из 10 записей ни одна не смешивает
получателей.

Нужного понятия не хватает. Рабочее место — «стол 2» с монитором,
системным блоком и клавиатурой — существует независимо от того, кто за
ним сидит. Сегодня, чтобы посадить за него нового человека, надо вернуть
на склад каждую вещь и выдать её заново.

Решения, зафиксированные с пользователем:

- **Стол — самостоятельное место.** Сотрудники меняются, техника
  остаётся на столе. Перепривязка стола к новому человеку не должна
  требовать перевыдачи вещей.
- **У стола один текущий хозяин**, и он может отсутствовать (стол
  свободен). Карточка сотрудника показывает два блока: «На рабочем
  месте» и «Лично на руках».
- Личная техника (ноутбук, телефон) по-прежнему выдаётся человеку
  напрямую — стол её не заменяет.

### Уже есть и переиспользуется

- **`AssetOps.mergeAllocation`** (`asset_ops.js`) — создание и увеличение
  записи о выдаче. Получатель определяется правилами `matches()`: у
  записи заполнено ровно одно поле. Четвёртый получатель добавляется
  сюда, и оба потребителя — окно выдачи и блок «Выдать сразу» в форме
  добавления техники — получают его сразу.
- **`getOperationPool(kind)`** (`app.js`) — откуда берутся позиции и как
  подписывается количество в окнах выдачи и возврата. Ветка по
  получателю уже есть, добавляется четвёртая.
- **`allocationLabel(entry)`** (`app.js:576`) — подпись получателя в
  таблицах и отчётах. Одно место на всё приложение.
- **`getEmployeeAllocation` / `getDepartmentAllocation` /
  `getSiteAllocation`** — поиск записи конкретного получателя;
  добавляется `getWorkplaceAllocation` по тому же образцу.
- **Система версионированных миграций** (`migrations.py`, сейчас 028) —
  применяется сама при старте, в том числе в собранном `.exe`.
- **`export_state()` / `import_state()`** (`server.py`) — состояние
  целиком отдаётся клиенту и целиком принимается обратно; новые сущности
  добавляются в оба конца, как это делалось для `sites` и
  `kit_templates`.
- **Экраны «Отделы» и «Объекты»** (`index.html`, `app.js`) — готовый
  образец простого справочника со списком, формой и удалением. Экран
  «Рабочие места» строится по нему.
- **Модалка карточки сотрудника** (`openEmployeeDetailsModal`,
  `app.js:1957`) — место, куда добавляются два блока.

## Не-цели этого этапа

- **Шаблоны комплектов.** Отдельный этап, опирающийся на этот:
  «применить шаблон к столу» без столов не существует. Формат хранения
  комплектов здесь не трогается.
- **Несколько сотрудников за одним столом.** Решение зафиксировано: один
  текущий хозяин.
- **История хозяев стола.** Кто сидел за столом раньше — не хранится.
  Смена хозяина фиксируется в журнале аудита, и этого достаточно.
- **Мобильное приложение.** Доступный остаток там считается суммой всех
  записей о выдаче независимо от получателя, поэтому арифметика не
  поедет и без изменений. Но карточка сотрудника на телефоне не покажет
  технику стола: её запрос (`db.js:305`) отбирает записи по
  `employee_id`. Это осознанное ограничение этапа, а не недосмотр.
- **Печать этикеток и акты** для стола. Акт выдачи оформляется как
  сейчас — на получателя.

## Модель данных

### Таблица `workplaces`

```sql
CREATE TABLE IF NOT EXISTS workplaces (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  employee_id TEXT REFERENCES employees(id),
  site TEXT NOT NULL DEFAULT '',
  notes TEXT NOT NULL DEFAULT ''
);
```

`employee_id` необязателен — свободный стол это нормальное состояние.
Внешний ключ без каскада: удаление сотрудника не должно молча уносить
стол вместе с техникой.

`name` — свободный текст («Стол 2», «Каб. 305, окно»). Уникальность не
навязывается на уровне схемы, но интерфейс предупреждает о совпадении
имени, как это сделано для дубликатов техники.

### Колонка `asset_allocations.workplace_id`

```sql
ALTER TABLE asset_allocations ADD COLUMN workplace_id TEXT NOT NULL DEFAULT ''
```

Пустая строка, а не NULL — так же, как у соседних `department` и `site`,
чтобы правила «заполнено ровно одно поле» проверялись единообразно.

### Миграции

- **029** — таблица `workplaces`.
- **030** — колонка `asset_allocations.workplace_id`.

Две миграции, а не одна: в проекте каждая отвечает за одно изменение
(017-023 заводят по таблице, 024-027 добавляют по колонке). Обе
идемпотентны и защищены `schema_version`.

## Попутное исправление: возврат из ремонта

`mergeAllocation` — не единственное место, создающее запись о выдаче.
Возврат из ремонта (`app.js:3692`) делает это сам:

```js
else asset.allocations.push({ employeeId: target.employeeId, quantity });
```

Запись получается другой формы — без `department` и `site`. Сейчас это
сходит с рук, потому что `undefined` в проверках ведёт себя как пустая
строка, но с добавлением четвёртого поля разнобой станет опаснее: запись
без `workplaceId` не совпадёт с правилами `matches()` предсказуемым
образом. Этот вызов переводится на `mergeAllocation` — он и без того
делал ровно её работу, только руками и с дублированием поиска
существующей записи.

Это не расширение задачи: форма записи о выдаче — предмет именно этого
этапа, и оставлять в ней второе, расходящееся определение нельзя.

## Правила получателя

`mergeAllocation` получает четвёртый ключ `workplaceId`. Порядок проверки
в `matches()`: сотрудник, отдел, объект, рабочее место — и запись
считается принадлежащей столу, только если остальные три поля пусты.
Сотрудник и его стол остаются **разными получателями**: иначе возврат от
человека списал бы количество со стола.

`allocationLabel(entry)` для записи стола возвращает `Место: {название}`,
а если у стола есть хозяин — `Место: {название} · {ФИО}`. Подпись одна
на таблицы, отчёты и историю.

## Интерфейс

### Экран «Рабочие места»

Новый пункт меню между «Объекты» и «Операции». Список столов, у каждого:
название, текущий хозяин (или «Свободен»), объект, количество единиц
техники. Форма создания — название, хозяин, объект, комментарий.

Карточка стола открывается по клику: техника на столе списком с
инвентарными номерами и количеством, кнопки «Выдать на это место» и
«Сменить хозяина».

### Смена хозяина

Ключевое действие ради которого всё затевается. Выбор нового сотрудника
в карточке стола меняет `employee_id` и **не трогает записи о выдаче** —
техника как числилась за столом, так и числится. Пишется запись в аудит
(`entity_type: "workplace"`, `action: "reassign"`) с прежним и новым
хозяином.

Освободить стол — тот же механизм с пустым сотрудником.

### Окна выдачи и возврата

Четвёртый вариант в переключателе получателя: «На рабочее место». Ниже —
выбор стола из всех, а не только свободных: доложить монитор на занятое
место — обычное дело. `getOperationPool("return")` получает ветку рабочего места с
подписью «на месте: N».

Панель «Уже на руках» в окне выдачи при выборе сотрудника дополняется
техникой его стола, отдельным подзаголовком — чтобы было видно, что
монитор у человека уже есть, пусть и через стол.

### Форма добавления техники

Блок «Выдать сразу» получает четвёртый вариант получателя тем же
переключателем. Никакой отдельной логики: он уже читает получателя через
`readAssetIssueRequest` и передаёт его в `mergeAllocation`.

### Карточка сотрудника

Два блока вместо одного: «На рабочем месте» (техника стола, за которым
он закреплён, с указанием названия стола) и «Лично на руках» (записи с
его `employee_id`). Если стола нет — первый блок не показывается.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Удаление стола, на котором есть техника | Запрещено с подсказкой: сначала вернуть технику на склад или перенести на другой стол. |
| Удаление сотрудника, за которым закреплён стол | Стол остаётся, хозяин очищается. Техника не трогается. |
| Стол с тем же названием | Предупреждение при сохранении, создание не блокируется — названия могут повторяться в разных кабинетах. |
| Выдача на место без выбранного стола | Отклоняется, как и выдача без выбранного сотрудника. |
| Запись о выдаче ссылается на несуществующий стол | Через интерфейс невозможно (удаление занятого стола запрещено), но состояние приходит и импортом. `allocationLabel` возвращает «Место удалено» — так же, как для неизвестного сотрудника. |
| Старая база без колонки `workplace_id` | Миграция 030 добавляет её со значением по умолчанию; существующие записи остаются записями сотрудников, отделов и объектов. |

## Тестирование

**`asset_ops.js` (node)**
- Первая выдача на стол заводит запись с заполненным только
  `workplaceId`.
- Повторная выдача на тот же стол увеличивает существующую запись.
- Выдача на стол не вливается в запись сотрудника, отдела или объекта, и
  наоборот — четыре перекрёстные проверки по образцу существующих.
- Выдача на стол без указанного стола отклоняется.

**Миграции (pytest)**
- 029 создаёт таблицу с ожидаемыми колонками; повторный прогон не падает.
- 030 добавляет колонку со значением по умолчанию; существующие записи
  сохраняют своих получателей.
- Обе применяются на legacy-базе, где `asset_allocations` ещё старой
  формы.

**Сервер (pytest)**
- `export_state()` отдаёт `workplaces` и `workplaceId` в записях о
  выдаче.
- `import_state()` сохраняет столы и возвращает их без изменений.
- Удаление сотрудника, за которым закреплён стол, не роняет импорт.

**Интерфейс (браузер, вручную)**
- Смена хозяина не меняет количество техники на столе.
- Карточка сотрудника показывает оба блока.
- Выдача и возврат на рабочее место на реальных данных.

## Порядок реализации

1. **Схема и сервер** — миграции 029 и 030, `workplaces` и `workplaceId`
   в состоянии. Ничего не ломает, всё остальное на этом стоит.
2. **`mergeAllocation`** — четвёртый получатель с тестами, перевод
   возврата из ремонта на неё же.
3. **Экран «Рабочие места»** — список, форма, карточка, смена хозяина.
4. **Окна выдачи и возврата** — четвёртый вариант получателя.
5. **Карточка сотрудника** — два блока.
