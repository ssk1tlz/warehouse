# Этап 1 дорожной карты: фундамент для массового запуска — дизайн

## Контекст

Проект (`D:\warehouse`) — локальная система складского учёта техники.
Сервер: `server.py` (чистый Python stdlib, `ThreadingHTTPServer`, без Flask),
SQLite (`warehouse.db`, зеркало схемы — `schema.sql`), десктоп-клиент
(`index.html` + `app.js`, упаковывается PyInstaller), мобильное приложение
(Capacitor 8 / Android, офлайн-first, синк раз в 15 сек — см.
`docs/superpowers/specs/2026-08-22-mobile-scanner-app-design.md`).

Сейчас: один общий необязательный пароль, Basic Auth поверх открытого HTTP,
включается только в сетевом режиме (`HOST=0.0.0.0`); при локальном режиме
(`HOST=127.0.0.1`) доступ вообще не ограничен. QR-сопряжение (`WHC1:`)
передаёт этот пароль открытым текстом. Миграции схемы — ad-hoc проверки
"если колонки нет — ALTER TABLE" внутри `init_db()`.

Это первый этап дорожной карты подготовки к многопользовательскому запуску.
Три задачи строго по порядку: версионные миграции БД (A) → учётные записи и
роли (B, использует A) → защита канала в LAN (C).

**Не-цели этого этапа** (пойдут отдельными промтами): разрешение конфликтов
одновременного редактирования, замена `alert()` на тосты, установщик Windows,
подпись сборок.

## Выбранные варианты (зафиксировано с пользователем)

- **Защита канала (Задача C): HTTP + HMAC**, а не HTTPS с самоподписанным
  сертификатом. Причина: мобильный нативный Android-слой сейчас нестабилен
  (в истории — реверты вендоринга плагинов из-за "startup bug"); вариант с
  TLS-пиннингом потребовал бы правки нативного `WebViewClient` и добавления
  `cryptography` в PyInstaller-сборку — риск сейчас неоправдан. TLS-пиннинг —
  кандидат для отдельного будущего этапа, когда мобильная нативная часть
  стабилизируется.
- **Модель QR-сопряжения: привязка к выбранному пользователю.** Admin в UI
  десктопа выбирает существующего пользователя перед генерацией QR; телефон
  получает токен именно этого пользователя. Прозрачно для `audit_log`.
- **Матрица прав на `POST /api/act`: admin + storekeeper, не viewer.**
  Причина: эндпойнт генерирует официальный документ (акт) из данных,
  переданных клиентом, — сервер их не сверяет с реальными `movements`. Это
  не пассивное чтение, а действие с последствиями вне БД, значит не
  подпадает под «только просмотр».

## Архитектура: границы модулей

`server.py` (690 строк) не раздувается дальше — новая логика в двух модулях:

- **`migrations.py`** — таблица `schema_version`, упорядоченный список
  миграций, `run_migrations(connection)`.
- **`auth.py`** — хэширование паролей, пользователи, сессии/токены,
  одноразовые коды сопряжения, проверка ролей, HMAC-подпись запросов.

`server.py` вызывает `run_migrations()` в `init_db()` и на каждом эндпойнте —
проверку роли из `auth.py` + (для не-loopback запросов) проверку подписи.

```
┌──────────────┐   логин/пароль (только loopback)   ┌────────────────────┐
│ Десктоп       │ ──────────────────────────────────▶│                     │
│ (app.js,      │◀──────────────────────────────────  │  server.py          │
│  127.0.0.1)   │   Bearer token                      │  + auth.py          │
└──────────────┘                                      │  + migrations.py    │
                                                       │  + SQLite           │
┌──────────────┐  QR (код+secret, вне сети)           │                     │
│ Телефон       │ ◀──── камера ───────────────────────│                     │
│ (Capacitor,   │ ──────────────────────────────────▶ │                     │
│  LAN IP)      │  Bearer token + X-Signature (HMAC)  └────────────────────┘
└──────────────┘
```

## Задача A — версионные миграции схемы

- Новая таблица `schema_version(version INTEGER PRIMARY KEY, applied_at TEXT)`.
- `migrations.py` определяет `MIGRATIONS: list[tuple[int, str, Callable[[Connection], None]]]`,
  пронумерованный по порядку. Первые миграции — переоформление существующих
  ad-hoc ALTER'ов один в один по смыслу и порядку, в котором они сейчас в
  `init_db()`: `repair_quantity`, `retired_quantity`, `min_quantity`,
  `warranty_end`, `price`, `repair_date`, `location`, `photo_url` (assets);
  `phone`, `site`, `status` (employees); `act_number`, `department`, `site`
  (movements); пересборка `asset_allocations` (колонка `department`, снятие
  `NOT NULL` с `employee_id`); `site` в `asset_allocations`; таблица `sites`;
  таблица `audit_log`; таблица `kit_templates`; таблица `mobile_action_log`.
  Далее — новые миграции для Задачи B (`users`, `sessions`,
  `pairing_codes`, колонка `actor` в `audit_log`).
- Каждая миграция идемпотентна (проверяет наличие колонки/таблицы перед
  изменением) — поэтому безопасно применять её и к старой базе, и "поверх"
  свежей `schema.sql` (там колонка уже есть — миграция становится no-op).
  Отдельного кодового пути "свежая база / старая база" не нужно:
  `init_db()` всегда выполняет `executescript(schema.sql)`, затем
  `run_migrations()` докатывает всё, чего не хватает.
- Перед применением хотя бы одной недостающей миграции — бэкап файла БД
  (переиспользуется `auto_backup()`, но с явной пометкой `pre_migration_`
  в имени файла), только если файл БД уже существовал на диске.
- `schema.sql` обновляется при каждой новой миграции (остаётся источником
  истины для целевой схемы).
- Тест: создать БД только из `schema.sql` (fresh) и БД, где выполнены все
  миграции поверх пустого файла (migrated) — сравнить `PRAGMA table_info`
  по каждой таблице и список таблиц (`sqlite_master`). Схемы должны
  совпадать. Отдельный тест — прогон миграций на копии реальной старой
  `warehouse.db` из `backups/` (без каких-то колонок) не должен падать и
  не должен терять строки.

## Задача B — учётные записи, роли, токены, QR-сопряжение

### Схема

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  username TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  salt TEXT NOT NULL,
  iterations INTEGER NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('admin','storekeeper','viewer')),
  is_active INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL
);

CREATE TABLE sessions (
  token TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  device_secret TEXT,              -- NULL для десктоп-сессий (loopback, HMAC не нужен)
  created_at TEXT NOT NULL,
  last_used_at TEXT NOT NULL,
  expires_at TEXT NOT NULL
);

CREATE TABLE pairing_codes (
  code TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  device_secret TEXT NOT NULL,
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL,        -- created_at + 10 минут
  used_at TEXT                     -- NULL пока не погашен; погашение однократно
);
```

`audit_log` получает колонку `actor TEXT NOT NULL DEFAULT ''` — логин
пользователя на момент действия (снапшот текстом, не внешний ключ: запись
должна остаться читаемой даже если пользователя потом удалили/переименовали).

Пароли: PBKDF2-HMAC-SHA256 (`hashlib.pbkdf2_hmac`), соль — `secrets.token_hex(16)`,
число итераций хранится в строке (задел на будущее повышение без миграции
существующих хэшей).

### Эндпойнты

| Эндпойнт | Роль | Назначение |
|---|---|---|
| `GET /api/setup-status` | публичный | `{needsSetup: bool}` — есть ли хоть один пользователь |
| `POST /api/setup` | публичный, только пока `users` пуста | создать первого admin |
| `POST /api/login` | публичный | `{username, password}` → `{token, expiresAt, role}` |
| `POST /api/logout` | любая роль | удаляет текущую сессию по токену из заголовка |
| `GET /api/users` | admin | список пользователей (без хэшей паролей) |
| `POST /api/users` | admin | создать пользователя |
| `PATCH /api/users/{id}` | admin | сменить роль / активность / пароль |
| `POST /api/pair/generate` | admin | `{userId}` → `{code, secret, expiresAt}` |
| `POST /api/pair` | публичный | `{code}` → `{token, expiresAt, role, username}` |
| `GET /api/state` | admin, storekeeper, viewer | без изменений |
| `GET /api/lan-info` | admin, storekeeper, viewer | без пароля в ответе (поле удаляется) |
| `POST /api/state` | admin, storekeeper | viewer → 403 |
| `POST /api/mobile/action` | admin, storekeeper | viewer → 403 |
| `POST /api/act` | admin, storekeeper | viewer → 403 (см. обоснование выше) |

Токен передаётся в заголовке `Authorization: Bearer <token>`. Срок жизни
токена — 90 дней, скользящее продление (`expires_at` обновляется) при каждом
успешном запросе с этим токеном; отзывается логаутом или деактивацией
пользователя (`is_active=0` → токен сразу недействителен, проверка на
каждом запросе через JOIN `sessions`→`users`).

### Поток сопряжения по QR

1. Admin открывает "Пользователи" в десктопе, выбирает существующего
   пользователя, жмёт "Сгенерировать QR для входа".
2. Десктоп вызывает `POST /api/pair/generate {userId}`, получает
   `{code, secret, expiresAt}`.
3. QR (`WHC1:{"url","code","secret"}`) — `url` берётся из `/api/lan-info`
   как раньше. Пароль в payload больше не участвует.
4. Телефон сканирует, сохраняет `serverUrl` + `deviceSecret` в
   Capacitor Preferences, отправляет `POST /api/pair {code}` (без подписи —
   на этом шаге секрета для проверки со стороны сервера ещё как бы "не
   предъявлено", но это ожидаемо: секрет телефон получил из того же QR, что
   и код, а не по сети — см. Задачу C).
5. Сервер проверяет код (существует, не просрочен, не погашен), помечает
   `used_at`, создаёт `sessions` с `device_secret` из `pairing_codes`,
   возвращает токен.
6. Телефон сохраняет токен, дальше работает как обычно — `sync.js` шлёт
   `Authorization: Bearer <token>` вместо Basic Auth.

### Десктоп UI

- Экран логина, если в `localStorage` нет валидного токена. Все `fetch()`
  в `app.js` начинают слать `Authorization: Bearer <token>`.
- Мастер создания первого admin, если `GET /api/setup-status` вернул
  `needsSetup: true` — показывается вместо экрана логина.
- Раздел "Пользователи" в настройках (виден только admin): список,
  создание, деактивация, смена роли, кнопка "Сгенерировать QR".
- UI прячет/дизейблит действия, недоступные текущей роли (viewer не видит
  кнопки выдачи/возврата и т.п.) — это UX-подсказка, реальная защита всегда
  на сервере.

## Задача C — HTTP + HMAC

`device_secret` передаётся ТОЛЬКО через QR (камера — канал вне LAN), никогда
по сети. Это ключевое отличие от "просто HMAC": даже если Bearer-токен
перехвачен сниффером на LAN, атакующий не сможет подписать новый запрос без
секрета, который по сети не передавался ни разу.

Схема подписи: строка для подписи —
`f"{method}\n{path}\n{timestamp}\n{sha256(raw_body).hexdigest()}"`,
HMAC-SHA256 c `device_secret`, заголовок `X-Signature: <timestamp>.<hex_digest>`.

Проверка на сервере — **только для запросов, пришедших не с loopback-адреса**
(`self.client_address[0] not in ("127.0.0.1", "::1")`). Десктоп всегда ходит
на `127.0.0.1` (уже так в `warehouse_tray.py`), поэтому его трафик исключение
не в смысле "менее защищён", а в смысле "физически не покидает машину — LAN
здесь ни при чём". Для трафика телефона (реальный LAN IP) подпись обязательна
для ЛЮБОГО запроса с валидным токеном, включая `GET /api/state`.

Окно времени — ±5 минут (допуск на рассинхрон часов телефона), запрос с
`timestamp` вне окна отклоняется. Отдельный кэш нонсов не заводим (YAGNI):
`POST /api/mobile/action` и так идемпотентен через существующий
`mobile_action_log` (повтор в пределах окна — не более чем безвредный
no-op), `GET /api/state` — просто чтение, повтор не вредит. Это осознанный
компромисс, задокументированный ниже.

**Честно задокументированное ограничение** (пойдёт в `docs/`, доступно
пользователю): HMAC защищает от подделки и (в пределах 5-минутного окна) от
повторного воспроизведения запроса, но НЕ от прослушивания — весь трафик
(включая данные склада и сотрудников) на LAN передаётся в открытом виде.
Полноценное шифрование канала — задача одного из следующих этапов.
Отдельно: `POST /api/pair` не подписывается (токена/секрета для проверки
у сервера ещё нет смысла требовать — это и есть момент первого доверия),
поэтому подпись не защищает и от чистого повтора точно перехваченного
пакета "как есть" — узкое окно риска на 10 минут жизни кода, только если
кто-то уже слушает LAN именно в момент сканирования QR. Снижается коротким
временем жизни кода и его одноразовостью (кто первый погасил код — тот и
получил токен, второй получит явную ошибку "код уже использован").

На мобильной стороне подпись считается через `crypto.subtle.sign('HMAC', …)`
(Web Crypto API, доступен в Capacitor WebView) — новых зависимостей не
требуется.

## Обработка ошибок

- Неверный логин/пароль → 401, без уточнения что именно неверно.
- Просроченный/погашенный код сопряжения → 400 с понятным сообщением,
  admin должен сгенерировать новый QR.
- Просроченный/отозванный токен → 401; десктоп показывает экран логина,
  мобильный переходит в состояние "нужно заново подключиться" и приостанавливает
  синхронизацию (не теряя офлайн-очередь).
- Деактивированный пользователь — токен уже недействителен на следующем
  запросе (проверка `is_active` в том же JOIN, что и срок действия).
- Невалидная/отсутствующая HMAC-подпись на не-loopback запросе → 401,
  отдельное сообщение об ошибке (чтобы отличать от "неверный токен" при
  отладке).
- Ошибка миграции при старте → сервер не поднимается, в консоль — понятная
  ошибка; pre-migration бэкап уже на диске, откат — восстановить его вручную.

## Критерии приёмки (без изменений от промта)

1. Старая `warehouse.db` (копия из `backups/`) мигрирует автоматически, с
   бэкапом, без потери данных.
2. Без входа API недоступно; роли реально ограничивают действия (viewer не
   может выдать технику).
3. Телефон подключается по QR за одно сканирование и работает офлайн как
   раньше; пароль открытым текстом нигде не передаётся и не хранится.
4. Канал защищён HTTP+HMAC-подписью; ограничение (нет защиты от
   прослушивания) описано в `docs/`.
5. Все тесты зелёные; EXE и APK собираются.
