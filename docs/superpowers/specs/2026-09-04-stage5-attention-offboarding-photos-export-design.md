# Этап 5 дорожной карты: продуктовые функции второй волны — дизайн

## Контекст

Этапы 1-4 в `master`: роли/токены, конфликт-детекция, WAL-БД, установщик,
подпись APK, опциональная проверка обновлений, режим инвентаризации,
пакетная печать этикеток. Складская логика (выдача, возврат, ремонт,
списание) не менялась ни разу за все четыре этапа — этот принцип
продолжается и здесь.

Уже есть и переиспользуется:
- **Поля в схеме, которые пока никто не читает**: `assets.min_quantity`,
  `assets.warranty_end`, `assets.photo_url`; `employees.status` (default
  `'active'`). Этап 5 — первый, кто их реально использует. **Ни одна из
  задач A/B/C/D не требует новой миграции БД на сервере.**
- **`GET /api/state` / `export_state()`** (`server.py`) — уже расширяется
  в каждом этапе новыми вычисляемыми полями (`currentVersion`,
  `latestVersion`, `activeInventorySession` — Этапы 3-4). Тот же приём
  используется здесь для `attentionItems`.
- **`/api/settings` + `config.json`** (`load_config`/`save_config`,
  `server.py`) — admin-only настройки, уже хранят `checkUpdates`
  (Этап 3). Пороги панели внимания добавляются туда же.
- **CSV-экспорт** (`app.js`, реестр техники) — client-side, BOM +
  `;`-разделитель под русский Excel, уже работает и открывается
  корректно. Прецедент для Задачи D — переиспользуем ту же пару
  helper-функций (`escape`/`triggerDownload`), не пишем ничего на
  сервере.
- **`act_generator.py`** — `.docx` через XML-подстановку в шаблон
  (`generate_act` — акт выдачи/возврата с сотрудником и таблицей позиций;
  `generate_inventory_act` — акт инвентаризации, Этап 4). Обе отдаются
  через эндпоинты `server.py`, не через HTML-печать.
- **Роль в `require_role()`** (сервер) и `data-requires-role` /
  `classList.toggle('hidden', role !== 'admin')` (десктоп/мобильный,
  паттерн из Этапа 4 для пункта "Инвентаризация") — тот же механизм
  скрывает новый пункт "Сотрудники".
- **`getAvailableQuantity(asset)`** (`app.js`) —
  `quantity - allocated - repairQuantity`. Единственное определение
  "свободного остатка" в проекте; на сервере Python-эквивалента ещё нет
  — Задача A первая, кому он нужен вне браузера.
- **Мобильная SQLite** (`mobile/www/js/db.js`) — `SCHEMA` создаёт таблицы
  идемпотентно (`CREATE TABLE IF NOT EXISTS`) при каждом `open()`, без
  guarded `ALTER` для новых таблиц (приём `inventory_scan_state`,
  Этап 4). Задача C заводит так же ещё одну таблицу.
- **`read_body()`** (`server.py`) читает сырое тело запроса по
  `Content-Length` — сейчас используется только для JSON. Multipart-
  парсинга в проекте нет и не нужен: Задача C передаёт бинарник как
  сырое тело запроса с `Content-Type: image/jpeg`, а не как
  `multipart/form-data` — тот же `read_body()`, просто не парсится как
  JSON.

## Не-цели этого этапа

- **Задача E (SSE) — не в этой спеке.** Опциональная по тексту
  промта ("если этап идёт хорошо"); решение по ней принимается отдельно
  после того, как A-D смержены в master, чтобы не тормозить основную
  ценность этапа риском совместимости SSE с `ThreadingHTTPServer`.
- **История фото.** Одно фото на актив, повторная съёмка заменяет
  предыдущее (решение зафиксировано с пользователем). Нет отдельной
  таблицы снимков, нет истории версий.
- **Доступ кладовщика к экрану сотрудника.** Только `admin` (решение
  зафиксировано с пользователем) — вопреки тому, что физически
  быстрый возврат чаще нужен кладовщику у стеллажа.
- **"Снятие"/расписание уведомлений о просроченной гарантии.** Панель
  "Требует внимания" — список по требованию (при загрузке `/api/state`),
  не push-уведомления, не email.
- **Печать через нативные драйверы принтера** для "ведомости на
  подпись" — как и акты Этапа 4, это `.docx`, не HTML-печать.
- **Ограничение количества/ротация файлов uploads/** сверх простого
  требования "не раздувать `/api/state`" — квоты на диск, автоочистка
  старых фото не входят в этот этап (файл при повторной съёмке просто
  перезаписывается, старый физически заменяется тем же путём).

## Выбранные варианты (зафиксировано с пользователем)

- **Одна спека на задачи A-D**, задача E — отдельным циклом
  спека→план→реализация после мерджа A-D. Причина: A-D делят паттерны
  (settings-пороги, `/api/state`-расширение, роль admin), E — рискованная
  и опциональная фича со своим собственным вопросом совместимости,
  которая не должна тормозить остальное.
- **Фото: замена, не история** (одно поле `photo_url` на актив, как
  сейчас).
- **Экран сотрудника — только `admin`.**
- **Порог "в ремонте дольше N дней" по умолчанию 14 дней** (настраивается
  через `/api/settings`, как и порог гарантии — 30 дней по тексту
  промта, тоже настраиваемый).
- **Синхронизация фото — отдельный upload-эндпоинт вне очереди
  `mobile_actions.py`.** Причина: очередь рассчитана на маленькие JSON-
  действия с дедупликацией по UUID; бинарник там means либо base64
  (+33% трафика, разбухание `mobile_action_log`), либо отдельный путь —
  выбран отдельный путь.
- **Панель "Требует внимания" считается один раз на сервере**
  (`compute_attention_items`), не дублируется в `app.js` и
  `screens.js` отдельными реализациями. Десктоп и мобильный только
  рендерят готовый список из `/api/state`.

## Архитектура: границы модулей

Новые файлы/эндпоинты (без единой новой таблицы/колонки на сервере):

- **`server.py`** — новая чистая функция `compute_attention_items(assets,
  settings)` (соседствует с `export_state()`, вызывается из него);
  результат кладётся в `attentionItems` поле `/api/state`. Новые ключи в
  `config.json` через существующие `handle_get_settings`/
  `handle_save_settings`: `attentionWarrantyDays` (default 30),
  `attentionRepairDays` (default 14).
- **`server.py`** — `PATCH`-семантика через существующий путь изменения
  сотрудника (`/api/state` целиком, как сейчас редактируются сотрудники)
  **или** отдельный `POST /api/employees/<id>/status` — решается в плане
  (см. "Открытые вопросы для плана" ниже); в любом случае `status`
  фильтрует уволенных из выпадающего списка выдачи на десктопе
  (`app.js`, чистая функция как `getAvailableQuantity`).
- **`server.py`** — `POST /api/assets/<id>/photo`: тело — сырые байты
  JPEG (`Content-Type: image/jpeg`, без multipart), admin/storekeeper.
  Сохраняет в `DATA_DIR/uploads/<asset_id>.jpg` (перезапись), обновляет
  `assets.photo_url` и бампает `rev` тем же путём, что обычное изменение
  актива. Новая константа в `paths.py`: `UPLOADS_DIR = DATA_DIR /
  "uploads"`.
- **`server.py`** — `GET /api/reports/handover-sheet?employeeId=...`
  (и/или `department=`/`site=`) — admin/storekeeper, `.docx` через
  `act_generator.py` (см. Задачу D — открытый вопрос про переиспользование
  `generate_act` вынесен в план).
- **`mobile/www/js/db.js`** — новая таблица `pending_photo_uploads` (id
  актива, локальный путь Capacitor Filesystem, `created_at`), тем же
  идемпотентным приёмом, что `inventory_scan_state`.
- **`mobile/www/js/settings.js`** — уже хранит `role` (добавлено в
  Этапе 4 для видимости пункта "Инвентаризация") — переиспользуется для
  видимости нового пункта "Сотрудники", новых полей не требует.
- **`mobile/www/js/screens.js` + `index.html`** — новый пункт нижней
  навигации "Сотрудники" (виден только admin, тот же
  `classList.toggle('hidden', role !== 'admin')`, что у
  `navInventoryBtn`); экраны: поиск/список сотрудника → его allocations →
  быстрый возврат (существующий `apply_return` через `pending_actions`,
  новый тип действия не нужен); для `status !== 'active'` — тот же экран
  в режиме "обходной лист" (чек-лист вместо произвольного возврата,
  итог "всё сдано"/"осталось N").
- **`app.js`/`index.html`/`styles.css`** — блок "Требует внимания" на
  главном экране десктопа (рендерит `attentionItems` из `/api/state`,
  клик — переход к карточке актива); в карточке сотрудника —
  управление `status` (активен/уволен); фильтрация уволенных в
  выпадающем списке выдачи; кнопки CSV-экспорта на экранах
  сотрудников/отделов/объектов/движений/остатков; кнопка "Ведомость на
  подпись" (скачивает `.docx` с сервера).
- **Мобильный: карточка актива** — кнопка "Сфотографировать"
  (`@capacitor/camera`, уже подключена), сжатие на устройстве (canvas,
  ≤1600px по длинной стороне, JPEG ~0.7), запись в
  `pending_photo_uploads` при отсутствии сети, фоновая докачка при
  восстановлении сети (тот же цикл опроса, что уже есть для
  `pending_actions`, но отдельный — фото не действие).
- **Показ фото**: `<img src="{serverUrl}/api/assets/<id>/photo">` и на
  десктопе, и на мобильном — обычное кэширование браузера/WebView,
  отдельного офлайн-кэша не пишем (бонус: не нужно гонять фото через
  `/api/state`, как и требует промт).

## Задача A — панель "Требует внимания"

**Сервер:** `compute_attention_items(assets, settings)` — чистая
функция, три вида сигналов: `warranty` (`warranty_end` в пределах
`attentionWarrantyDays` от сегодня, включая уже истёкшие — оба случая,
как в промте: "истекает в ближайшие 30 дней / уже истекла"), `low_stock`
(`available < min_quantity`, где `available` — Python-эквивалент
`getAvailableQuantity`), `long_repair` (актив со статусом "в ремонте"
дольше `attentionRepairDays`, считается от `repair_date`). Каждый пункт
— `{type, assetId, assetName, detail}`. Вызывается из `export_state()`,
результат кладётся в `attentionItems`.

**Десктоп:** блок на главном экране, сгруппированный по трём типам,
клик по пункту открывает карточку актива (существующий переход, как из
поиска).

**Мобильный:** бейдж-счётчик (как непрочитанные уведомления) + простой
список тех же `attentionItems` без действий — только для чтения,
переход к действиям не входит в MVP этой задачи.

**Настройки:** `attentionWarrantyDays`/`attentionRepairDays` — новые
поля в модалке `/api/settings` (десктоп), рядом с `checkUpdates`.

## Задача B — экран сотрудника (только admin) + обходной лист

**Мобильный:** новый пункт "Сотрудники" в нижней навигации, виден
только admin. Поиск/выбор сотрудника → список его `asset_allocations`
(количество, актив) → кнопка возврата на каждой позиции → тот же
`apply_return`, что и с карточки актива, через `pending_actions`.

Если у выбранного сотрудника `status !== 'active'` — экран явно
показывает режим "Обходной лист": тот же список allocations, но с
чек-боксами "возвращено" и сводкой "сдано X из Y" / "всё сдано".
Функционально это тот же `apply_return`, разница только в
представлении (акцент на полноте, а не на произвольном частичном
возврате).

**Десктоп:** в карточке сотрудника — переключатель `status`
(активен/уволен). Выпадающий список выбора сотрудника при выдаче
техники фильтрует `status === 'active'` — чистая функция с тестом на
граничный случай "уволенный с непустыми allocations всё ещё существует
в списке сотрудников, но не предлагается для новой выдачи".

## Задача C — фото техники

**Мобильный:** кнопка "Сфотографировать" на карточке актива →
`@capacitor/camera` → сжатие на устройстве (canvas resize ≤1600px по
длинной стороне, JPEG quality ~0.7, ориентировочно <300KB) → попытка
`POST /api/assets/<id>/photo` сразу; при неудаче (нет сети) — запись
локального пути в `pending_photo_uploads`, фоновая докачка при
восстановлении сети очищает очередь на успехе.

**Сервер:** сохраняет тело запроса как `DATA_DIR/uploads/<asset_id>.jpg`
(перезапись при повторной съёмке), обновляет `assets.photo_url` (путь/
URL для `GET`), бампает `rev`. Отдача — `GET /api/assets/<id>/photo`
(бинарный ответ, `Content-Type: image/jpeg`), 404 если файла нет.

**Показ:** карточка актива на десктопе и мобильном — `<img>` на URL
эндпоинта, без дополнительного офлайн-кэширования (браузер/WebView
кэширует сам).

## Задача D — экспорт отчётов

**CSV (client-side, без нового серверного кода):** переиспользуется
паттерн `app.js` (`escape` + `triggerDownload`, BOM + `;`). Три вида
данных, все уже загружены в `state` на клиенте: ведомость по
сотруднику/отделу/объекту (фильтр по `asset_allocations`), движения за
период (фильтр `movements` по датам из уже загруженного списка), остатки
со стоимостью (`quantity * price` по позициям). Кнопки экспорта — на
соответствующих существующих экранах десктопа (карточка сотрудника/
отдела/объекта, список движений, реестр).

**Печатная форма "ведомость на подпись":** `.docx` через
`act_generator.py`, endpoint `GET /api/reports/handover-sheet`. **Открытый
вопрос для плана:** `generate_act(employee, items, is_issue=True)` уже
строит ровно такую таблицу (сотрудник + позиции), но с фразой шаблона
под конкретную транзакцию выдачи ("выдал(а)" сегодняшним числом) — для
"текущей ведомости на руках" это семантически неверная формулировка.
План должен явно решить: (а) завести третий вариант `ACTION_PHRASE`
("числится за", без "сегодня выдал") и дёшево переиспользовать
`generate_act`, или (б) новый шаблон/функция по образцу
`generate_inventory_act`. Предпочтение дизайна — вариант (а), если
шаблон это позволяет без искажения остального текста.

## Обработка ошибок

- **Разрыв сети во время фото** — фото не теряется (локальный файл +
  запись в `pending_photo_uploads`), докачивается при восстановлении
  сети, как `pending_actions`.
- **Повторная фотосъёмка до завершения предыдущей докачки** — новая
  запись в очереди заменяет/отменяет старую для того же `asset_id`
  (нет смысла докачивать устаревшее фото поверх более нового) — план
  должен зафиксировать точный приём (например, `INSERT OR REPLACE` по
  `asset_id` как первичному ключу очереди).
- **Два одновременных изменения `status` сотрудника** (десктоп +
  другой десктоп/сессия) — обычный конфликт по `rev`, как и остальные
  поля сотрудника/актива (существующий механизм Этапа 2).
- **CSV с пустым результатом фильтра** (например, у сотрудника нет
  allocations) — экспорт всё равно срабатывает, файл с одними
  заголовками, не ошибка.
- **`/api/assets/<id>/photo` для несуществующего/списанного актива** —
  404/409 по аналогии с остальными asset-эндпоинтами.

## Тестирование

- **Чистые функции с тестами (Python, `pytest`)**: `compute_attention_items`
  — граничные даты гарантии (ровно на пороге, за днём до, за днём после,
  уже истёкшая), граница `attentionRepairDays`, `low_stock` при
  `available == min_quantity` (не сигнал) и `available < min_quantity`
  (сигнал).
- **JS (`node --test`, где применимо)**: фильтрация уволенных сотрудников
  в выпадающем списке выдачи (десктоп), сборка обходного листа
  ("всё сдано" при пустом остатке allocations).
- **Сервер**: маршруты `/api/settings` (новые пороги round-trip),
  `/api/assets/<id>/photo` (upload → GET возвращает те же байты,
  повторная загрузка перезаписывает), `/api/reports/handover-sheet`
  (структура `.docx`, как уже тестируется `act_generator.py`).
- **Мобильное**: `node --test` для очереди `pending_photo_uploads`
  (запись/докачка/очистка), фильтрации allocations на экране
  сотрудника. Реальную камеру/сжатие автотестами не покрыть — ручная
  проверка (см. критерии приёмки).
- **Десктоп**: без автотестов (`app.js`/`index.html` без обвязки — тот
  же прецедент, что в Этапах 2-4), ручная проверка в финальной задаче
  этапа.

## Критерии приёмки (без изменений от промта)

1. Панель внимания показывает ровно те позиции, что подпадают под
   пороги (тест на граничные даты).
2. Обходной лист: уволенный сотрудник с техникой на руках → все
   возвраты проведены с телефона → на руках пусто; уволенный не
   предлагается при выдаче.
3. Фото, снятое офлайн, после появления сети оказывается на десктопе.
4. CSV открывается в Excel с корректной кириллицей и цифрами.
5. Все тесты зелёные; EXE и APK собираются.
