# Мобильное приложение для сканирования QR-этикеток — дизайн

## Контекст

В этой же сессии на этикетки техники добавили настоящую генерацию QR-кодов
(vendored `qrcode-lib.js`, замена Code-128) вместо штрих-кода. Изначально
планировали, что скан обычной камерой телефона откроет веб-страницу с
информацией об активе (маршрут `/a/<id>` на локальном сервере) — этот план
был согласован по дизайну, но не реализован: пользователь переключился на
запрос полноценного мобильного приложения раньше, чем сказал «делай».

Мотивация: при сканировании этикетки нужно сразу видеть, за кем закреплено
оборудование (и статус/историю), и иметь возможность тут же выполнить
действие (выдать/принять возврат/отправить в ремонт) — без похода к
десктопу. Приложение должно работать и при подключении к складской Wi-Fi
сети, и без неё.

Проект (`D:\warehouse`) — склад IT-техники, эксплуатируется одним человеком.
Технологический стек: Python `http.server` (без Flask) + ванильный JS без
сборщика + SQLite, десктоп собирается PyInstaller. Вся экосистема сейчас
без внешних зависимостей и build-шагов (кроме одного Google Font в CSS).

## Цель и не-цели

**Цель.** Android-приложение (устанавливается как `.apk` вручную, без Google
Play), которым пользуется сам владелец склада с 1-2 телефонов:
сканирует QR на этикетке → видит карточку актива (статус, держатель,
последние движения) → при необходимости сразу оформляет выдачу/возврат/
ремонт. Работает и в складской Wi-Fi сети (сразу применяет действия), и вне
её (действия уходят в очередь и применяются при появлении связи).

**Не-цели (сознательно не делаем сейчас):**
- iOS — не требуется.
- Несколько личных аккаунтов сотрудников / разграничение прав — приложением
  пользуется один админ, действия не нужно атрибутировать разным людям.
- Публикация в Google Play — только прямой `.apk`.
- Полный CRUD (создание/редактирование активов, сотрудников, отделов) с
  телефона — только просмотр + выдача/возврат/ремонт/возврат из ремонта/
  списание.
- Автообнаружение сервера в сети (mDNS и т.п.) — адрес вводится вручную один
  раз при настройке.
- «Настоящая» фоновая синхронизация (Android WorkManager и т.п.) — синк по
  событию (открытие приложения / появление сети), этого достаточно для
  объёма и темпа использования.

## Архитектура: обзор

```
┌─────────────────────┐        LAN (Wi-Fi) или офлайн        ┌──────────────────────┐
│   Android-приложение │ ───────────────────────────────────▶ │  server.py (существ.) │
│   (Capacitor: JS/     │   GET /api/state (переиспользуем)   │  WarehouseHandler      │
│   HTML/CSS + плагины) │   POST /api/mobile/action (новое)   │  + Basic Auth (уже есть)│
│                      │ ◀───────────────────────────────────  │  + SQLite (warehouse.db)│
│  Локальный кэш:      │                                       └──────────────────────┘
│  SQLite (плагин)      │
│  + pending_actions    │
│  очередь              │
└─────────────────────┘
```

Мобильное приложение — второй клиент той же БД (первый — desktop-приложение
на app.js). Схема данных и правила бизнес-логики (кто сколько чего держит,
как считается доступное количество) не меняются — переносятся/дублируются
туда, где они нужны каждому клиенту.

## A. Формат QR

Меняю относительно уже обсуждавшегося (URL-подход не реализован, отменяю
его в пользу более простого варианта, раз основной сценарий — сканирование
самим приложением, а не произвольной камерой):

QR кодирует `WH1:<asset.id>` — короткий магический префикс + внутренний
стабильный id актива (не инвентарный номер, который пользователь может
менять). Префикс нужен, чтобы приложение отличало «наш» QR от случайного
постороннего кода в кадре. Печатная подпись под QR-квадратом на этикетке
не меняется — остаётся человекочитаемым инвентарным номером (уже
реализовано, `qrHtml`/`qrModuleGrid` в `app.js` кодируют `bcData`; меняется
только то, что вычисляется как `bcData` для самого QR — печатная подпись
берётся из отдельной переменной, как уже сделано).

## B. Сервер — изменения

### B.1 Синхронизация (без изменений на сервере)

Мобильное приложение использует уже существующий `GET /api/state` — там уже
есть всё нужное: активы (с `allocations`), сотрудники, отделы, объекты,
последние движения, версия состояния. Тот же Basic Auth (LAN-пароль),
что уже защищает этот маршрут при включённом сетевом режиме.

### B.2 Новый маршрут: `POST /api/mobile/action`

Единственное дискретное действие за раз (не полная замена состояния, в
отличие от десктопного `POST /api/state`) — так очередь офлайн-действий
может отправлять их по одному, в своём порядке, без необходимости иметь
свежий полный снимок состояния для вычисления диффа.

**Запрос:**
```json
{
  "clientActionId": "uuid-v4-сгенерированный-на-телефоне",
  "type": "issue | return | repair | repair_return | retire",
  "assetId": "ast_...",
  "employeeId": "emp_... | null",
  "department": "строка | \"\"",
  "site": "строка | \"\"",
  "quantity": 1,
  "date": "2026-08-22",
  "notes": "строка | \"\""
}
```

**Бизнес-правила** — переносятся из существующих клиентских обработчиков в
`app.js` (это единственный источник истины на сегодня, правила должны
остаться идентичными, чтобы desktop и mobile считали одинаково):
- `issue` ← `handleIssueSubmit` (проверка доступного остатка, создание/
  увеличение allocation, запись в `movements`)
- `return` ← `handleReturnSubmit` (проверка, что у держателя действительно
  числится нужное количество, уменьшение allocation, чистка нулевых
  allocations)
- `repair`, `repair_return`, `retire` ← аналогичные обработчики
  (`handleRepairSubmit`, `handleRepairReturnSubmit`, `handleRetireSubmit`)

Реализуется на сервере (Python, атомарная транзакция SQLite), а не путём
получения полного состояния и повторного использования JS-логики — так
исключается класс багов, где мобильный клиент действует по устаревшим
данным.

**Идемпотентность:** сервер хранит недавние `clientActionId` (например, в
`app_meta` или отдельной небольшой таблице с TTL) и при повторном
поступлении того же id возвращает ранее сохранённый результат вместо
повторного применения — защищает от двойного оформления при обрыве связи
после отправки, но до получения ответа (частый сценарий при синке через
нестабильный Wi-Fi).

**Ответ:** обновлённое состояние актива (или ошибка с понятным текстом —
«недостаточно доступного количества», «актив не найден» и т.п.), плюс
новая версия состояния — тем же способом, каким уже отвечает
`POST /api/state`.

Маршрут защищён тем же `check_auth()`.

## C. Мобильное приложение — офлайн-хранилище и синк

**Локальная БД** (Capacitor SQLite-плагин), зеркало нужного подмножества
серверной схемы: `assets`, `employees`, `departments`, `sites`,
`allocations`, последние 3 `movements` на актив (для карточки — столько же,
сколько показывается в разделе D).

**Очередь:** отдельная таблица `pending_actions` — `clientActionId`, тип,
payload, `createdAt`, `status` (`pending` / `syncing` / `failed`),
`serverError` (nullable, для показа пользователю, если сервер отклонил
действие — например, «уже возвращено кем-то ещё»).

**Цикл синхронизации** (при открытии приложения и при обнаружении сети):
1. Выгрузить `pending_actions` на сервер по одному, в порядке создания;
   успешные — убрать из очереди; отклонённые — оставить с `serverError`.
2. Подтянуть `GET /api/state`, перезаписать локальный кэш (полная
   перезапись проще инкрементального диффа и оправдана размером датасета —
   пара сотен активов).

**Локальные записи:** действие, сделанное офлайн, сразу пишется в
`pending_actions` и оптимistично применяется к локальному кэшу (интерфейс
сразу показывает «выдано»), чтобы не создавалось ощущение, что офлайн-режим
не работает. После успешного синка локальное состояние сверяется с
авторитетным ответом сервера.

## D. Экраны (MVP)

1. **Сканер** — открывается сразу при запуске (или по кнопке из списка
   недавних), камера + рамка, распознаёт `WH1:<id>`.
2. **Карточка актива** — статус (пилюля), категория, инв./серийный номер,
   локация, **«Закреплено за»** (крупно, самое заметное), последние 3
   движения, кнопки действий — показываются только применимые к текущему
   статусу (например, «Выдать» не показывается, если и так полностью
   выдано).
3. **Форма действия** — минимальная: сотрудник/отдел/объект (для issue/
   return), количество (по умолчанию — весь доступный/весь числящийся
   остаток), дата (по умолчанию сегодня), заметка (необязательно).
4. **Индикатор очереди** — сколько действий ждут отправки, статус последней
   синхронизации, ручной «Повторить» для действий с ошибкой.

## E. Подключение к серверу

Экран настройки при первом запуске: IP:порт склад-сервера (тот же LAN IP,
что показывает `setup_lan.bat`/консоль сервера) и LAN-пароль. Сохраняется в
настройках приложения (`Capacitor Preferences`), меняется вручную при
необходимости (смена IP роутером и т.п.). Без автообнаружения — оправдано
масштабом (1-2 телефона под контролем владельца).

## Риски и открытые вопросы

- **Смена LAN IP.** Если IP склад-компьютера меняется (перезагрузка
  роутера, DHCP), приложение перестаёт находить сервер, пока не поправят
  адрес в настройках вручную. Не устраняется в MVP (см. «не-цели» —
  автообнаружение).
- **Порт в файрволе.** Уже решено существующим `setup_lan.bat` (открывает
  порт 8765) — mobile ничего нового не требует.
- **Дублирование бизнес-логики.** Правила выдачи/возврата теперь будут в
  двух местах (`app.js` для десктопа, новый Python-код для мобильного
  API) — осознанный компромисс ради надёжной офлайн-очереди (см. B.2).
  При изменении правил на десктопе нужно не забыть синхронизировать
  серверную копию.
- **Печать этикеток задним числом.** Все уже напечатанные до этой сессии
  этикетки кодируют инвентарный номер (Code-128) или голый номер (первая
  версия QR) — они не будут содержать `WH1:` префикс и не распознаются
  новым приложением как валидный QR. Требуется перепечатать этикетки для
  активов, которые нужно сканировать приложением. Не блокирует запуск —
  можно печатать по мере необходимости.

## Проверка (после реализации)

- Юнит-тесты бизнес-правил на сервере (Python) — issue/return/repair/
  retire, включая пограничные случаи (недостаточный остаток, несуществующий
  актив, повторный `clientActionId`).
- Ручная проверка полного цикла на реальном телефоне: скан → карточка →
  действие онлайн; затем — авиарежим → скан → действие → выход из
  авиарежима → подтверждение, что действие применилось на сервере и видно
  в desktop-приложении.
- Проверка, что старые (напечатанные до перехода на `WH1:` префикс)
  этикетки не приводят к ложным срабатываниям/крашам сканера — просто не
  распознаются, приложение показывает понятное сообщение «не похоже на
  этикетку склада».
