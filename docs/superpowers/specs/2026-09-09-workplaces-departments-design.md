# Рабочие места — разделение по отделам (дизайн)

## Контекст

Продолжение [`2026-09-07-workplaces-design.md`](2026-09-07-workplaces-design.md),
по которому уже реализована базовая версия: таблица `workplaces`, экран
списком, форма добавления/редактирования, привязка техники через
`asset_allocations.workplace_id` и `mergeAllocation`, блоки «На рабочем
месте» / «Лично на руках» в карточке сотрудника. На живой базе сейчас
133 сотрудника, 24 отдела, 228 единиц техники и **1** рабочее место —
функция почти не использовалась, миграция безопасна.

Источник задачи — `Промпт_Рабочие_места.md`: превратить плоский список
столов в список, сгруппированный по отделам, с собственным полем отдела
у рабочего места (не путать с отделом сотрудника), внутренним кодом,
поиском и понятным статусом техники.

Промпт написан как для типового приложения с REST CRUD и серверной
пагинацией на каждую сущность. Реальное приложение (`server.py` —
самодельный `http.server`, не Flask) везде использует другую модель: весь
стейт грузится и сохраняется одним блоком (`GET`/`POST /api/state`),
группировка и фильтрация — на клиенте. При текущем масштабе данных это
работает нормально для отделов и сотрудников, и этот этап продолжает ту
же модель — никаких новых REST-эндпоинтов, пагинации или backend-поиска
не заводится.

## Не-цели

Переносятся без изменений из прошлого этапа — этот этап их не трогает:

- Шаблоны комплектов на рабочее место.
- Несколько сотрудников на одном рабочем месте.
- История прошлых хозяев места (только текущий, смена — в audit_log).
- Доработки мобильного приложения (оно по-прежнему не видит технику
  стола отдельно).
- Печать этикеток/актов на рабочее место.

Дополнительно вне рамок этого этапа:

- Отдельная подробная карточка рабочего места (промпт, раздел 29,
  помечен как «можно реализовать отдельным этапом»).
- Серверная пагинация и REST-эндпоинты — см. обоснование выше.

## Модель данных

`workplaces` получает два новых столбца обычными
`_add_column_if_missing`-миграциями (33, 34), без пересоздания таблицы:

```sql
ALTER TABLE workplaces ADD COLUMN department TEXT NOT NULL DEFAULT '';
ALTER TABLE workplaces ADD COLUMN code TEXT NOT NULL DEFAULT '';
```

Итоговая форма:

```
workplaces
  id           TEXT PRIMARY KEY
  name         TEXT NOT NULL
  code         TEXT NOT NULL DEFAULT ''   -- новое, server-owned, вида WP-0001
  department   TEXT NOT NULL DEFAULT ''   -- новое, свободный текст (см. ниже)
  employee_id  TEXT REFERENCES employees(id)
  site         TEXT NOT NULL DEFAULT ''   -- переиспользуется как «Объект/локация»
  notes        TEXT NOT NULL DEFAULT ''
```

**`department` — текст, а не `department_id`.** Ровно так же, как
`employees.department`, `movements.department` и
`asset_allocations.department` — ни одна из них не ссылается на
`departments.id`, все хранят имя отдела строкой и сверяются со списком
`departments` только для выпадающего списка в форме. Отдельная
FK-связь для одних только рабочих мест завела бы второй, несовместимый
способ хранить одно и то же понятие.

**`site` не дублируется новым полем `location`.** Промпт описывает
«Объект/локацию» одним полем, куда можно и выбрать существующий объект,
и вписать конкретное место («Офис, 2 этаж», «Стол у окна») — это ровно
то, чем `site` уже является (свободный текст, не FK на `sites`). Меняется
только элемент формы: `<select>` становится комбобоксом (`<input
list="...">` + `<datalist>` из `state.sites`), схема не трогается.

**Код (`code`) — простой сквозной номер `WP-0001`, `WP-0002`…**, без
попытки угадать префикс по названию отдела (в отличие от техники, где
префикс определяется категорией — `asset_codes.guess_prefix` — у отдела
нет однозначного соответствия трёхбуквенному коду на латинице).
Назначается сервером, клиент его не отправляет и не редактирует — как
`assets.rev` / `label_printed_at` / `photo_url` сейчас.

Миграция 34 при апгрейде проставляет `code` уже существующим строкам (на
проде — одной) той же нумерацией, что и создание новых.

## Backend (`server.py`, `migrations.py`)

### Генерация кода

Новая маленькая функция (аналог `asset_codes.next_number`, но без
угадывания префикса): сканирует `SELECT code FROM workplaces`, разбирает
`WP-(\d+)`, берёт максимум + 1. Вызывается внутри `import_state`:

- если `id` уже существовал (есть в `old_workplaces`) — `code`
  сохраняется из старой строки, что бы ни прислал клиент;
- если `id` новый — присваивается следующий номер, счётчик увеличивается
  в пределах одного вызова `import_state`, чтобы несколько новых
  рабочих мест в одном сохранении не получили одинаковый код.

Реализуется той же техникой, что уже применена для `assets` в
`import_state` (сравнение с `old_assets`, сохранение server-owned полей).

### Валидация (`validate_state`)

Расширяется существующая функция (уже проверяет `employees` и `assets`):
для каждого объекта в `payload["workplaces"]`:

- обязателен непустой `name` (после `strip()`);
- обязателен непустой `department`;
- дубль **в пределах одного отдела** (`name.strip().lower()` +
  `department`) отклоняется с сообщением `Рабочее место с таким
  названием уже существует в этом отделе.` — это меняет прежнее
  поведение (было: предупреждение, создание не блокировалось), решение
  подтверждено пользователем: в прошлый раз отдела как измерения не
  было, теперь дубль реально проверяется по паре имя+отдел, а не только
  по имени, так что переезд на блокировку не ломает исходный сценарий
  «одинаковое имя в разных кабинетах».

Фронтенд дублирует обе проверки до сабмита (как сейчас сделано для
отделов и техники), чтобы пользователь не ждал ответа сервера ради
опечатки.

### Права доступа

Ничего нового: сохранение по-прежнему идёт через `/api/state`, которое
уже требует `require_role(user, ("admin", "storekeeper"))`. Отдельных
проверок для рабочих мест не требуется.

## Существующая бизнес-логика — сохраняется без изменений

Закодирована в прошлом этапе, промпт её не упоминает явно, но ломать
нельзя:

- **Один сотрудник — одно рабочее место.** Назначение на новое место
  снимает сотрудника со старого (`handleWorkplaceSubmit`, `app.js:2631`).
- **Удаление места с техникой запрещено**, а не просто отвязывает её —
  `deleteWorkplace` (`app.js:2685`) сначала проверяет
  `getWorkplaceAssets(workplaceId)`.
- **Удаление сотрудника не удаляет место** — только освобождает
  `employee_id` (уже покрыто тестом `test_deleting_employee_keeps_the_
  workplace`).
- Аудит: `entity_type: "workplace"`, действия `create` / `reassign`
  (смена хозяина) уже пишутся. Этот этап добавляет `update` для
  остальных изменяемых полей (название, отдел, объект/локация,
  комментарий) — по той же схеме, что у отделов
  (`addAuditEntry("department", id, "update", { name })`).

## Frontend (`index.html`, `app.js`, `styles.css`)

Тёмная тема не изобретается заново: `[data-theme="dark"]` уже даёт
`#080c14` фон, `#1a2236` карточки, полупрозрачные синие границы
(`--line`) — тот самый «Dark Admin Dashboard» из промпта. Новый экран
собирается на существующих классах (`.panel`, `.panel-header`,
`.list-item`, `.chip`, `.empty-state`, `showToast`, `showConfirm`), а не
на новой палитре.

### Форма «Добавить рабочее место»

Двухколоночная (как сейчас), с новым полем **Отдел** (`<select>` из
`state.departments`, обязательное) первым в списке полей. При выборе
сотрудника, если поле «Отдел» ещё не тронуто вручную, подставляется
`employee.department` как значение по умолчанию (промпт, раздел 19) —
но пользователь может тут же переключить его на другой отдел. Поле
«Объект/локация» становится комбобоксом (datalist по `state.sites` +
свободный ввод) вместо строгого `<select>`.

### Вкладки-фильтры отделов

Новый компонент (в проекте такого ещё нет): горизонтальный ряд
кнопок-вкладок «Все отделы N», затем по одной на каждый отдел из
`state.departments` со счётчиком количества его рабочих мест (0
включительно — пустые отделы не скрываются, промпт раздел 20). Строится
на `.chip`/кнопочных стилях, которые уже есть.

### Список рабочих мест — группировка по отделам

Каждый отдел — сворачиваемая карточка-панель (`.panel`) с таблицей
внутри: Рабочее место (название + `code`) · Объект/локация · Сотрудник
(или «Свободно») · Оборудование (список инвентарных номеров +
агрегированный статус) · Действия (Изменить/Удалить). Состояние
свёрнутости — в памяти вкладки (по умолчанию первый отдел с
результатами открыт, промпт раздел 28), не персистится на сервере.

На мобильном (используется существующий брейкпоинт employees-секции,
`max-width: 720px`) таблица заменяется карточками по образцу
`.emp-card`.

### Сортировка

Отделы идут в порядке, в котором их уже отдаёт `export_state()`
(`SELECT id, name FROM departments ORDER BY name`) — дополнительно
сортировать на клиенте не нужно. Рабочие места внутри отдела по
умолчанию — по названию. Над таблицей каждого отдела — выпадающий список
«Сортировать по»: название, сотрудник (ФИО), объект/локация, количество
техники (по убыванию) — переключение пересчитывает порядок строк только
внутри открытой группы, на клиенте, без обращения к серверу.

### Статус техники

Не хранится, вычисляется на рендере из уже приходящих данных:
`getWorkplaceAssets(workplaceId)` (уже есть) даёт список выданной месту
техники; если хотя бы одна позиция встречается в `state.attentionItems`
или имеет `status === "repair"`/`"retired"` — статус «⚠ Требует
проверки», иначе (при непустом списке) «🟢 Всё в порядке», при пустом —
«Оборудование не назначено».

### Поиск

Одно поле, переиспользует существующий `matchesSearch()` по названию
места, `code`, ФИО сотрудника, названию отдела, объекту/локации и
инвентарным номерам техники на месте. При непустом запросе автоматически
разворачиваются отделы, где есть совпадения (остальные сворачиваются).

### Удаление

Тот же `showConfirm()` с текстом из промпта («Вы действительно хотите
удалить рабочее место «…»?») и то же правило блокировки при наличии
техники (см. раздел про сохранённую бизнес-логику) — просто с более
точным текстом ошибки.

### Состояния интерфейса

Переиспользуются существующие паттерны: `.empty-state` для «рабочих мест
пока нет» / «по вашему запросу ничего не найдено», `showToast` для
успеха/ошибки сохранения. Отдельного skeleton-состояния загрузки не
требуется — состояние приходит вместе с первым `GET /api/state` при
старте экрана, как и везде в приложении.

## Тестирование

- **`tests/test_migration_workplaces.py`** — миграции 33/34: колонки
  добавляются идемпотентно, `code` бэкофиллится существующим строкам,
  не наступает на уже занятые номера.
- **`tests/test_server_workplaces.py`** — round-trip с `department` и
  `code`; `code` сохраняется при повторном сохранении и не
  перезаписывается клиентским значением; новый `id` получает
  следующий свободный номер; несколько новых мест в одном payload не
  сталкиваются кодами.
- Новый тест на `validate_state`: пустой `department` отклоняется;
  дубль `name`+`department` отклоняется с точным текстом ошибки; тот же
  `name` в другом `department` проходит.
- **Интерфейс (браузер, вручную, по чек-листу промпта раздел 33):**
  создание/редактирование/удаление, назначение и снятие сотрудника,
  смена отдела (место переезжает в другую группу), поиск с
  автораскрытием, пустые отделы, счётчики, статус техники, мобильная
  верстка, права доступа (viewer не может сохранять), отсутствие
  дублей, отсутствие регрессий в выдаче/возврате техники и карточке
  сотрудника.

## Риски и совместимость

Аддитивные изменения (новые колонки с дефолтами) — не ломают ни
`export_state`/`import_state` для других сущностей, ни мобильное
приложение (оно получает новые поля в `/api/state` и просто их
игнорирует, как уже игнорирует часть существующих). Данных мало (1
запись), миграция без риска потери.

## Порядок реализации

1. **Схема и сервер** — миграции 33/34, генерация `code`, расширение
   `validate_state`, обновление `export_state`/`import_state`.
   Ничего не ломает, всё остальное стоит на этом.
2. **Форма и бизнес-правила на клиенте** — поле «Отдел», комбобокс
   объекта/локации, блокировка дублей, аудит `update`.
3. **Группировка и вкладки отделов** — список вместо плоского,
   счётчики, сворачивание.
4. **Поиск и автораскрытие.**
5. **Статус техники и мобильная адаптация.**
