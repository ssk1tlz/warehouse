# Этап 4 дорожной карты: инвентаризация и печать этикеток — дизайн

## Контекст

Этапы 1-3 в `master`: роли/токены, конфликт-детекция, WAL-БД, установщик,
подпись APK, опциональная проверка обновлений. Складская логика (выдача,
возврат, ремонт, списание) не менялась ни разу за все три этапа — этот
принцип продолжается и здесь.

Уже есть и переиспользуется:
- **Сканер** (`mobile/www/js/scanner.js`) — три одноразовых режима:
  `scanOnce` (свой QR `WH1:`/`WHC1:`), `scanLabelBarcode` (заводской
  штрихкод), `scanLabelPhoto` (OCR фото этикетки). Все три открывают
  модальное окно плагина `@capacitor-mlkit/barcode-scanning` и закрывают
  его после ОДНОГО распознанного кода.
- **Плагин сканера уже поддерживает непрерывный режим.** Проверено:
  `@capacitor-mlkit/barcode-scanning` v8.1.0 (установлен,
  `mobile/node_modules`) экспортирует `startScan()` +
  `addListener('barcodeScanned', ...)` + `stopScan()` — камера рисуется
  за WebView, приложение просто прячет свою разметку классом на
  время скана. Новая зависимость не нужна.
- **Очередь действий** (`mobile_actions.py`) — единый диспетчер
  `apply_action()`, каждое действие (`apply_issue`/`apply_return`/...)
  — одна атомарная операция, дедуплицируется по UUID действия на
  сервере. Синхронизация — раз в 15 секунд, офлайн-безопасна.
- **Печатные акты** — НЕ HTML-печать. `act_generator.py` собирает
  `.docx` подстановкой в шаблон (`word/document.xml` внутри zip),
  отдаётся через `POST /api/act` (`handle_act_request`, `server.py`).
- **QR на десктопе** — `qrcode-lib.js` (ванильный, уже в репозитории,
  MIT), сейчас рисует один QR на карточке актива.
- **Роли** — `admin`/`storekeeper`/`viewer`, `require_role()` на сервере,
  `data-requires-role` в разметке десктопа.

## Не-цели этого этапа

- **Печать через нативные драйверы принтера.** Только окно печати
  браузера + `@media print`. Термопринтер 58мм — просто другой пресет
  размера этикетки в том же CSS-макете, не отдельная интеграция.
- **Потоковая отправка сканов на сервер.** Каждый скан живёт только
  локально на телефоне, пока сессия открыта. На сервер уходит одно
  действие `inventory_complete` по завершении — как любой другой акт
  в проекте.
- **Параллельные инвентаризации.** Одна открытая сессия на весь склад;
  секционирование по участкам/местам не входит в этот этап.
- **Доступ кладовщика к инвентаризации.** Только `admin` — решение
  зафиксировано с пользователем при брейнsторминге, вопреки
  рекомендации автора дизайна (обычно кладовщик физически ходит по
  складу).
- **Персистентное "не показывать снова" для конкретной инвентаризации**
  на десктопе/мобильном — не запрошено.
- **Миграция существующих одноразовых сканов** (`scanOnce` и т.д.) на
  непрерывный режим. Они остаются как есть — непрерывный скан нужен
  только новому экрану инвентаризации, где смысл именно в потоке
  кодов подряд.

## Выбранные варианты (зафиксировано с пользователем)

- **Одно действие `inventory_complete` на сессию**, не поштучные
  действия на каждый скан. Соответствует тому, как уже устроены все
  остальные операции склада (акт = одно действие), не раздувает
  дедуп-очередь, и кладовщик успевает разобраться с расхождениями до
  отправки, а не транслирует сырые сканы в реальном времени.
- **Состояние сессии — в локальной таблице SQLite на телефоне**, не в
  оперативной памяти приложения. Тот же приём, что и у `pending_actions`
  — переживает закрытие/убийство приложения.
- **Одна открытая сессия на сервер.** `POST /api/inventory/start`
  отвечает `409`, если сессия уже открыта — вместо секционирования по
  участкам. Проще, без риска гонок между двумя параллельными
  подсчётами одного и того же актива.
- **Пометка "не на своём месте" — в MVP.** Третий статус скана наравне
  с "найдено"/"лишнее", а не отдельная задача на будущее.
- **Только `admin`.**
- **Акт инвентаризации — через `act_generator.py`, новой функцией**,
  не через overload существующей `generate_act()`. У акта выдачи/
  возврата другая форма данных (сотрудник, is_issue) — совмещать
  сигнатуры хуже, чем завести соседнюю функцию с тем же механизмом
  подстановки в `.docx`-шаблон. **Открытый вопрос для реализации:**
  нужен отдельный `.docx`-шаблон под акт инвентаризации (структура
  таблиц другая: найдено/не найдено/лишнее/не на месте, без
  сотрудника) — это работа с содержимым шаблона, не только с кодом;
  план должен явно завести на неё отдельный шаг.
- **Печать этикеток переиспользует `qrcode-lib.js` как есть.** Новый
  JS-код только собирает сетку `<div>`-ов с QR + текстом и один
  `@media print` блок в `styles.css`.

## Архитектура: границы модулей

Новые файлы и таблицы:

- **Миграция 026** (`migrations.py`, после `_migrate_025_assets_rev`) —
  `inventory_sessions` (id, started_at, finished_at, started_by,
  status: `open`/`finished`) и `inventory_scans` (session_id, asset_id,
  status: `found`/`wrong_location`, found_location). "Лишнее"
  (неизвестные коды) в БД не хранится — это не актив; список уходит
  только внутри самого действия `inventory_complete` и в акт.
- **Миграция 027** — `assets.label_printed_at` (TEXT, для фильтра "не
  печатались ранее" в мастере печати).
- **`mobile_actions.py`** — новый обработчик `apply_inventory_complete`
  в диспетчере `apply_action()`: закрывает открытую сессию, пишет
  `inventory_scans`, готовит данные для акта.
- **`server.py`** — новые маршруты: `POST /api/inventory/start`
  (admin, 409 если уже открыта), `GET /api/inventory/sessions` (список
  для десктопа), `GET /api/inventory/sessions/<id>/act` (docx). Текущая
  открытая сессия видна через `/api/state` (как версия обновлений в
  Этапе 3) — десктопу и телефону не нужен отдельный поллинг.
- **`act_generator.py`** — новая функция `generate_inventory_act(...)`
  и (вероятно) новый `.docx`-шаблон.
- **`mobile/www/js/scanner.js`** — новые функции
  `startInventoryScan(onBarcode)`/`stopInventoryScan()` поверх
  `BarcodeScanner.startScan`/`addListener('barcodeScanned')`/`stopScan`.
  Существующие `scanOnce`/`scanLabelBarcode`/`scanLabelPhoto` не трогать.
- **`mobile/www/js/db.js`** — новая таблица локального кэша для
  состояния текущей сессии (какие asset_id уже отмечены и с каким
  статусом), в дополнение к уже существующей `pending_actions`.
- **`mobile/www/js/screens.js` + `index.html`** — пункт "Инвентаризация"
  в нижней навигации (виден только admin — та же проверка роли, что
  скрывает другие admin-пункты), экраны: старт, скан (полноэкранная
  камера + счётчик), расхождения, подтверждение отправки.
- **Десктоп (`app.js`/`index.html`/`styles.css`)** — новая модалка
  "Инвентаризации": список сессий, текущая открытая с live-прогрессом
  (через уже существующий поллинг `/api/state`), кнопка "Акт" на
  завершённой.
- **Десктоп: мастер печати этикеток** — новый экран/модалка, фильтры
  (все/категория/место/вручную/непечатавшиеся), сетка предпросмотра,
  печать через `window.print()` + `@media print`.
- **`server.py`** — `POST /api/assets/label-printed` (bulk-проставить
  `label_printed_at` для списка id после реальной печати).

## Задача A — режим инвентаризации

**Мобильный поток:** admin открывает "Инвентаризация" → если сессия уже
открыта (её же или чужая, раз сессия одна на сервер) — сразу продолжает
её, а не создаёт новую. Иначе — "Начать инвентаризацию" →
`POST /api/inventory/start`. Экран скана: `startInventoryScan` держит
камеру открытой, каждый `barcodeScanned` парсится тем же
`parseWarehouseQr`, что и `scanOnce`; свой известный QR → отметка
"найдено" (повторный скан того же — не дублируется, тихо игнорируется);
нераспознанный/чужой формат → в список "лишнее". Счётчик "найдено X из
Y" обновляется по каждому событию. Кнопка "Завершить" останавливает
`stopInventoryScan`, ведёт на экран расхождений: "не найдено" (актив в
базе, не отсканирован), "лишнее" (отсканировано, не в базе или списано),
"не на своём месте" (найден location ≠ учётный) — на каждой позиции
опциональная пометка нового location. "Отправить" собирает
`inventory_complete` и кладёт в ту же очередь `pending_actions`, что и
остальные действия — офлайн-безопасно, ничем не отличается от выдачи/
возврата с точки зрения синхронизации.

**Сервер:** `apply_inventory_complete` в транзакции закрывает
`inventory_sessions` (status → finished, finished_at), пишет
`inventory_scans`, отмечает списки "лишнее"/"не найдено" внутри JSON
результата действия (для акта — не как отдельные строки БД). Если
сессию уже закрыл кто-то другой (гонка при двух админах, оба видевших
одну открытую сессию) — обрабатывается как обычный конфликт действия
(существующий механизм 409 из Этапа 2), клиенту показывается стандартный
экран разрешения конфликта очереди.

**Десктоп:** модалка "Инвентаризации" — список завершённых + текущая
открытая. У завершённой — дата, исполнитель (username, роль из Этапа 1),
кнопка "Акт" → `generate_inventory_act` → скачивание `.docx`.

## Задача B — печать QR-этикеток пачкой

**Мастер печати** (десктоп, новая модалка): выбор позиций — все /
фильтр по категории или месту (переиспользует существующие
фильтр-компоненты списка активов) / вручную (чекбоксы в таблице) /
"без этикетки не печатались ранее" (`label_printed_at IS NULL`).
Предпросмотр — сетка `<div>` по числу выбранных позиций, каждая: QR
(`qrcode-lib.js`, кодирует `WH1:<asset_id>` — та же схема, что уже
используется для одиночной этикетки), название, инвентарный номер.

**Размер этикетки** — пресеты в CSS: А4-сетка 3×8 (24 этикетки на лист,
`@page { size: A4 }`) и лента термопринтера 58мм (`@page { size: 58mm
auto }`, один столбец). Печать — `window.print()`, весь макет уже
подготовлен через `@media print` (скрыть всё, кроме сетки этикеток).
После реального клика "Печать" (событие `afterprint` либо явная кнопка
"Готово, отметить как напечатанные") — `POST /api/assets/label-printed`
с списком id, обновляет `label_printed_at`.

**На карточке одной единицы техники** — кнопка "Напечатать этикетку",
открывает тот же мастер с одной предвыбранной позицией.

## Обработка ошибок

- **Разрыв сети посреди сессии** — сканы не теряются (локальная
  таблица), `inventory_complete` просто ждёт восстановления сети в
  общей очереди действий, как любое другое действие.
- **Убийство/закрытие приложения посреди скана** — при следующем
  открытии экрана инвентаризации состояние читается из локальной
  таблицы, счётчик показывает то же "X из Y".
- **Два admin видят одну открытую сессию** — второй, попытавшийся
  начать новую, получает 409 с данными текущей открытой (не ошибка "уже
  идёт", а явное продолжение — интерфейс просто показывает её как
  текущую).
- **Неизвестный/битый QR при скане инвентаризации** — не ошибка, тихо
  попадает в "лишнее" (как и описано в промте задачи).
- **Печать без выбранных позиций** — кнопка "Печать" неактивна, пока
  список пуст.

## Тестирование

- **Чистые функции с тестами (Python и/или JS, по месту)**:
  сверка расхождений (сканы vs активы → найдено/не найдено/лишнее/не на
  своём месте) — вероятно серверная часть `apply_inventory_complete`,
  тестируется как остальные `apply_*` в `mobile_actions.py`; выбор
  позиций для печати по фильтрам — чистая функция, тестируется
  отдельно от рендера.
- **Сервер**: миграции 026/027, маршруты `/api/inventory/*`
  (включая 409 на двойной старт), генерация акта (структура docx —
  как уже тестируется `act_generator.py`, если там есть тесты; если
  нет — завести по аналогии).
- **Мобильное**: `node --test` для функции сверки расхождений и логики
  локального кэша сессии. Реальную камеру/`startScan` автотестами не
  покрыть — здесь только смоук на уровне "события слушателя корректно
  обновляют состояние", как уже делается для `describeUpdate` и т.п.
- **Десктоп**: без автотестов (`app.js`/`index.html` без обвязки — тот
  же прецедент, что в Этапах 2-3), ручная проверка в финальной задаче
  этапа.

## Критерии приёмки (без изменений от промта)

1. Полный цикл офлайн: старт инвентаризации → сканы → расхождения →
   синхронизация → результат и акт на десктопе.
2. Повторные сканы не дублируются; неизвестные QR попадают в "лишнее";
   прерванная сессия продолжается после перезапуска приложения.
3. Лист этикеток печатается и сканируется приложением с бумаги.
4. Все тесты зелёные; EXE и APK собираются.
