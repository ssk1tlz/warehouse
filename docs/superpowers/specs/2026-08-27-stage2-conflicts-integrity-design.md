# Этап 2 дорожной карты: конфликты, целостность синхронизации и человеческие ошибки — дизайн

## Контекст

Этап 1 (`docs/superpowers/specs/2026-08-27-stage1-foundation-design.md`) уже в
`master`: версионные миграции (`migrations.py`, таблица `schema_version`,
версии 1-24), учётные записи/роли/токены (`auth.py`), HTTP+HMAC-подпись
канала. Этот этап строится поверх — новые миграции продолжают нумерацию с 25.

Сейчас: `POST /api/state` (десктоп, выгрузка всего состояния целиком,
срабатывает на каждое поле реестра с debounce) защищён только грубой
оптимистической блокировкой на уровне ВСЕЙ базы — `app_meta.state_version`,
инкрементируется на любое изменение, сравнивается целиком. `POST
/api/mobile/action` (точечные действия с телефона: issue/return/repair/
repair_return/retire/edit) вообще не имеет версионирования на уровне записи:
`apply_edit` в `mobile_actions.py` безусловно перезаписывает поля актива —
классическое "последняя запись молча побеждает". Целостность БД: `foreign_keys
= ON` уже включён при каждом соединении, WAL не включён, `PRAGMA
integrity_check` не выполняется никогда. Автобэкапы пишутся в `backups/`
(`auto_backup()`, ротация `MAX_BACKUPS=30` только для `warehouse_*.db`), но
интерфейса восстановления нет — только ручное копирование файла. Мобильные
ошибки — `alert()` в шести местах `screens.js`.

## Не-цели этого этапа

- **`rev` не добавляется в `employees`.** Единственный путь, где сейчас
  возможен настоящий конфликт "одна и та же запись правится в двух местах
  одновременно" — мобильное действие `edit`, а оно трогает только `assets`
  (в `mobile_actions.py` нет ни одного действия, редактирующего сотрудника).
  Добавлять версионирование туда, где нет потребителя — мёртвый вес. Если
  появится мобильное редактирование сотрудников — рассмотреть отдельно.
- Диалог со сравнением "что именно изменилось" перед перезаписью конфликта не
  строим — "Повторить поверх" просто переотправляет то же действие с новым
  `baseRev`, без визуального diff'а. Достаточно для сценария из критериев
  приёмки; полноценный diff — кандидат на будущий этап, если понадобится.
- Шифрование канала и разрешение конфликтов на уровне `POST /api/state`
  (десктоп vs десктоп) — вне объёма, там уже есть `state_version`, и этот
  этап её не трогает.
- Восстановление из бэкапа не требует loopback (в отличие от `/api/setup` из
  Этапа 1) — это не bootstrap-действие, роль `admin` + HMAC-канал уже
  достаточная защита, а admin обычно и так на loopback (десктоп).

## Выбранные варианты (зафиксировано с пользователем)

- **Версия записи: целочисленный `rev`**, а не `updated_at`. Не зависит от
  точности часов телефона (Этап 1 уже показал, что часам телефона доверять
  нельзя — отсюда ±5-минутное окно HMAC). Сравнение "та же версия или нет" —
  просто `==`.
- **Провал `PRAGMA integrity_check` при старте → сервер не поднимается**,
  чёткое сообщение в консоль со списком файлов в `backups/`. Симметрично
  поведению Этапа 1 при ошибке миграции. Восстановление в этом случае —
  вручную скопировать файл бэкапа и перезапустить; одно-кликовый
  восстановитель (Задача C) в этом случае недоступен, т.к. сервер не запущен
  — это принятое ограничение, не баг.

## Архитектура: границы модулей

Новых модулей не создаём — этап встраивается в существующие четыре точки:

- **`migrations.py`** — миграция 25 (`assets.rev`).
- **`mobile_actions.py`** — `apply_edit` требует `baseRev`, при несовпадении
  поднимает новое исключение `EditConflictError` (подкласс
  `MobileActionError`) с текущими значениями редактируемых полей и `rev`;
  сам же и бампает `rev` при успешном применении. Остальные `apply_*`
  (issue/return/repair/repair_return/retire) не трогают ни `rev`, ни поля,
  которые он охраняет (`name/category/inventoryNumber/...`) — им нечего
  бампать, изменений не требуется.
- **`server.py`** — `init_db()`: WAL + `integrity_check`; `handle_mobile_action`
  различает `EditConflictError` (409) от обычной `MobileActionError` (400);
  `import_state()` бампает `rev` тех активов, у кого изменилось хотя бы одно
  редактируемое поле; новые эндпойнты `GET /api/backups`,
  `POST /api/backups/restore`.
- **`app.js`** — модалка "Резервные копии" (admin), в стиле уже существующей
  "Пользователи".
- **`mobile/www/js/`** — `db.js` (новый статус очереди `'conflict'`),
  `sync.js` (обработка 409), `screens.js` (две кнопки на конфликтующем пункте
  очереди, замена `alert()` на тосты), новый `toast.js`.

### Важный нюанс: `rev` и `POST /api/state`

`POST /api/state` (десктоп) переписывает **весь** реестр активов на каждое
сохранение (debounce на ввод в реестре — это часто, не раз в синхронизацию).
Если бампать `rev` безусловно для каждого актива при каждом таком сохранении,
любая случайная правка десктопом ЛЮБОГО другого актива будет провоцировать
ложный конфликт на телефоне, ожидающем синхронизации по совершенно другой
записи. Поэтому `import_state()` бампает `rev` актива только когда реально
изменилось хотя бы одно из полей, которые умеет трогать мобильный `edit`:
`name, category, inventoryNumber, serialNumber, location, purchaseDate,
warrantyEnd`. Это ровно тот же список полей, которым владеет
`apply_edit` в `mobile_actions.py` — совпадение не случайно, это одна и та же
семантика "кто-то поменял карточку" с двух разных путей записи. Изменения
`quantity`/`status`/`price`/остальных полей (их правит только выдача/возврат/
ремонт/списание, не мобильный `edit`) `rev` не трогают.

`state_version` (глобальный, Этап 1 не менялся) и `assets.rev` (новый,
точечный) — два независимых механизма для двух разных гонок: первый не
даёт двум десктоп-сохранениям затереть друг друга целиком, второй — не даёт
мобильному точечному `edit` затереть более свежую правку конкретной карточки.
Они не заменяют друг друга и оба остаются в силе.

## Задача A — обнаружение конфликтов редактирования

### Схема

```sql
ALTER TABLE assets ADD COLUMN rev INTEGER NOT NULL DEFAULT 0;
```

Миграция 25 в `migrations.py`, обычный `_add_column_if_missing`-паттерн.

### Контракт `POST /api/mobile/action` для `type: "edit"`

- Действие теперь обязано нести `baseRev` (текущий `rev`, известный
  телефону на момент, когда пользователь начал править карточку).
- Сервер сравнивает `baseRev` с текущим `assets.rev`. Совпадает → применяет
  правку как раньше, `rev` инкрементируется на 1, `mobile_action_log`
  кеширует успешный ответ как обычно (дедупликация не трогается).
- Не совпадает → **HTTP 409**, тело
  `{"error": "Карточка была изменена на сервере.",
    "currentAsset": {"rev": N, "name": ..., "category": ..., "inventoryNumber": ...,
    "serialNumber": ..., "location": ..., "purchaseDate": ..., "warrantyEnd": ...}}`.
  Действие в `mobile_action_log` НЕ кешируется (не выполнено) — повторный
  запрос с тем же `clientActionId` после того, как пользователь нажмёт
  "Повторить поверх" (с новым `baseRev`), обрабатывается как новая попытка.
- Действия `issue/return/repair/repair_return/retire` версию не несут и не
  проверяют — они и так отклоняются по остаткам через существующий
  `MobileActionError` → 400. Здесь только тест-регрессия: убедиться, что
  ошибка insufficient-stock доходит до статуса `'failed'` в очереди
  (уже так по коду, формально закрепляем тестом).

### Очередь на мобильном (`db.js` / `screens.js`)

- Новый статус `pending_actions.status = 'conflict'` (наравне с
  `pending/failed/synced`). `flushQueue` в `sync.js`: ответ 409 на `edit`
  → `Db.markActionConflict(clientActionId, currentAsset)` (новая функция,
  хранит присланный `currentAsset` в `server_error`-подобном поле как JSON,
  чтобы кнопка "Повторить поверх" знала актуальный `rev`), не считается ни
  `flushed`, ни `failed` — отдельный счётчик `conflicted` в возвращаемой
  сводке `flushQueue`.
- Экран очереди (`screens.js`): пункт со статусом `'conflict'` рендерится
  отдельно от `'failed'` (другой цвет/подпись — "Конфликт: карточка изменена
  на сервере") с двумя кнопками:
  - **"Повторить поверх"** — берёт сохранённый `currentAsset.rev` как новый
    `baseRev`, оставляет остальные поля правки пользователя как есть,
    переводит статус в `'pending'`, следующий `Sync.run()` отправит заново.
  - **"Отменить"** — удаляет запись из `pending_actions` насовсем (новая
    `Db.cancelAction(clientActionId)`), без обращения к серверу (действие и
    так не было применено).

## Задача B — целостность БД

- `get_connection()` в `server.py`: добавить `PRAGMA journal_mode = WAL`
  сразу после существующего `PRAGMA foreign_keys = ON`.
- Аудит транзакций: `import_state` и `handle_mobile_action` уже оборачивают
  мутацию в `BEGIN` (используют `with get_connection() as connection:`,
  который сам коммитит/откатывает на выходе из блока — подтверждено чтением
  кода). Новый код восстановления (Задача C) оборачивается так же.
- `init_db()`: после `run_migrations()` — `PRAGMA integrity_check`. Результат
  не `"ok"` (одна строка) → сервер завершает работу с ненулевым кодом,
  печатает в консоль: что произошло, путь к `warehouse.db`, список файлов в
  `backups/` с датами (отсортированы, самый свежий первым), и что делать
  (скопировать выбранный файл поверх `warehouse.db`, перезапустить).

## Задача C — восстановление из бэкапа в один клик

### Эндпойнты (роль `admin`, доступны и по LAN — не bootstrap-действие)

| Эндпойнт | Назначение |
|---|---|
| `GET /api/backups` | Список файлов `backups/*.db` (оба вида — `warehouse_*.db` и `pre_migration_*.db`), каждый — `{filename, createdAt, sizeBytes}`, отсортированы по дате убывания |
| `POST /api/backups/restore {filename}` | Восстановить БД из указанного файла |

### Поток восстановления

1. Проверка, что `filename` — один из реально перечисленных `GET
   /api/backups` (защита от path traversal — не принимать произвольный путь).
2. Копия кандидата во временный файл, `PRAGMA integrity_check` НА КОПИИ —
   если битая, 400 с понятной ошибкой, `warehouse.db` не тронут.
3. `STATE_LOCK` (тот же, что использует `POST /api/state` и
   `/api/mobile/action` — гарантирует отсутствие гонки с текущими записями).
4. Автоснимок текущей `warehouse.db` с явной пометкой `pre_restore_*.db`
   (аналог `pre_migration_backup()` из Этапа 1 — восстановление тоже
   обратимо).
5. Атомарная подмена `warehouse.db` копией кандидата.
6. `migrations.run_migrations()` поверх восстановленного файла (мог быть
   старым, до текущей версии схемы).
7. Ответ `{"ok": true}`; активные токены/сессии не инвалидируются
   намеренно — восстановление БД не про безопасность канала.

### Ротация

Существующая логика прунинга в `auto_backup()` расширяется на ВСЕ файлы
`backups/*.db` разом (единый `MAX_BACKUPS`), а не только на `warehouse_*.db` —
иначе `pre_migration_*.db` и новые `pre_restore_*.db` копятся бесконечно.

### UI (десктоп, только `admin`)

Модалка "Резервные копии" в стиле уже существующей "Пользователи": таблица
файлов (дата, размер), кнопка "Восстановить" в каждой строке с `confirm()`
(тот же паттерн, что уже используется для удаления объектов в `app.js`).
После успешного восстановления — принудительная перезагрузка состояния
(`boot()`).

## Задача D — человеческие сообщения вместо alert() (только мобильное)

- Новый `mobile/www/js/toast.js`, без зависимостей: `showToast(message, type)`
  (`type`: `info | error`), рендерит плавающий блок, авто-скрытие через
  несколько секунд, несколько тостов не перекрывают друг друга (очередь/стек).
  Немного CSS в `mobile/www/style.css`.
- Все 6 текущих `alert(...)` в `screens.js` заменяются на `showToast(...)`.
- `describeError(err)`: серверные ошибки (`MobileActionError.message`,
  включая новый конфликт) уже человеческие и на русском — показываются как
  есть. Сетевые ошибки/таймауты/нет соединения — фиксированный человеческий
  текст ("Нет связи с сервером. Действие сохранено и будет отправлено
  автоматически.") вместо технического текста исключения. Ни один "сырой"
  HTTP-код или текст исключения JS не должен долетать до пользователя.
- Подтверждение "Действие в очереди" — тостом после каждой постановки
  действия в очередь (issue/return/repair/repair_return/retire/edit),
  независимо от того, онлайн телефон сейчас или нет.

## Обработка ошибок

- Конфликт версии (`edit`, `baseRev` не совпал) → 409, `currentAsset` в теле,
  действие не кешируется в `mobile_action_log`, статус очереди `'conflict'`.
- Нехватка остатка/невалидные ссылки (`issue/return/repair/...`) → 400,
  как раньше, статус очереди `'failed'`, текст ошибки уже человеческий.
- `integrity_check` проваливается при старте → сервер не поднимается,
  подробная консольная ошибка, ручное восстановление (см. "Не-цели").
- Восстановление из битого файла-кандидата → 400 до какой-либо мутации
  `warehouse.db` (проверка на копии, не на оригинале).
- Восстановление из файла, которого нет в списке `GET /api/backups`
  (подделанный/произвольный путь) → 400, без попытки прочитать файл.
- Любая мобильная ошибка (сетевая, серверная, сканера) — тост, не `alert()`
  и не сырой код/стектрейс.

## Тестирование

- `pytest`: `assets.rev` бампается на успешный `apply_edit`; количественные
  `apply_*` (issue/return/repair/repair_return/retire) НЕ бампают `rev`
  (тест на негатив — они не трогают охраняемые им поля); `import_state`
  бампает `rev` только при изменении редактируемых полей и НЕ бампает при
  изменении только `quantity`/`status`; конфликт
  `baseRev` → 409 + `currentAsset` с актуальным `rev`; повторная попытка с
  новым `rev` после конфликта проходит; `integrity_check` проваливается на
  намеренно испорченной копии БД → сервер не стартует с понятной ошибкой;
  `GET/POST /api/backups*` — список, восстановление, ротация, защита от
  восстановления битого/несуществующего файла, `pre_restore_*.db` создаётся
  перед откатом; WAL реально включён (`PRAGMA journal_mode` возвращает
  `wal`).
- `node --test`: `flushQueue` заводит статус `'conflict'` на 409 и не путает
  его с `'failed'`; `Db.retryConflict`/`Db.cancelAction`; `toast.js` —
  рендер/авто-скрытие/стек нескольких тостов; ни один `alert(` не остаётся в
  `mobile/www/js/*.js` (grep-тест).

## Критерии приёмки (без изменений от промта)

1. Сценарий "телефон офлайн правит, десктоп правит ту же запись, телефон
   синхронизируется" → правка десктопа цела, на телефоне конфликт виден,
   есть выбор "повторить поверх / отменить".
2. Выдача при нехватке остатка даёт понятную ошибку в очереди.
3. Восстановление из снапшота работает и само делает бэкап перед откатом.
4. В мобильном коде нет ни одного `alert()`; каждая операция подтверждается
   тостом.
5. Все тесты зелёные; EXE и APK собираются.
